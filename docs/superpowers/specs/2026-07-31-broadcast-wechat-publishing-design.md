# Broadcast 公众号发布验收优化设计

## 目标

让 `broadcast` 在使用 Wechatsync 投递公众号草稿时，区分“工具执行成功”和“草稿内容完整可用”，避免把未落地的封面、未验证的移动端排版或其他缺失项报告为已完成。

本次只优化发布流程和验收规则，不修改 Wechatsync、不新增发布脚本、不接管平台登录与接口实现。

## 当前问题

现有流程在四重内容验收后把发布包交给 Wechatsync，并根据工具结果记录草稿状态。真实投递暴露出两个缺口：

1. Markdown 在桌面端可读，但宽代码块和字符图在公众号移动端横向溢出。
2. CLI 接受并显示了封面参数，但微信公众号适配器没有把封面写入草稿；流程却曾把它记录为“封面已上传”。

根因是发布前只检查了素材是否存在，发布后只检查了工具是否返回成功，没有逐项确认目标平台中的实际结果。

## 目标流程

```text
平台稿与素材完成
  ↓
内容四重验收
  ↓
平台可渲染性检查
  ↓
发布适配器能力预检
  ↓
用户授权后保存草稿
  ↓
草稿落地验收
  ↓
报告自动完成项、未确认项和人工处理项
```

### 平台可渲染性检查

公众号标准文章在投递前额外检查：

- 宽代码块、ASCII 图和宽表格是否适合手机屏幕；
- 图片路径、格式和尺寸是否可被发布入口处理；
- 封面与正文插图是否为不同用途的明确素材；
- 无法稳定适配的结构是否已改为普通文本或移动端图卡。

该检查只处理平台呈现，不重复事实、传播和风格验收。

### 发布适配器能力预检

逐项记录当前发布入口对以下内容的状态：

| 内容项 | 状态 |
|---|---|
| 标题 | 支持 / 不支持 / 未确认 |
| 摘要 | 支持 / 不支持 / 未确认 |
| 正文 | 支持 / 不支持 / 未确认 |
| 正文图片 | 支持 / 不支持 / 未确认 |
| 封面 | 支持 / 不支持 / 未确认 |

命令存在某个参数，只能证明入口接受该参数，不能证明目标平台适配器会应用它。首次使用或版本变化后，应结合当前文档、适配器实现、预览或实际草稿确认能力。

明确不支持但允许人工补充的内容，不阻止草稿投递；必须在投递前告知用户，并在结果中保留人工处理项。

### 草稿落地验收

发布状态使用以下层级：

1. `已提交`：发布入口接受请求。
2. `已保存草稿`：有草稿创建结果。
3. `草稿内容已确认`：目标平台中的关键内容已经逐项确认。
4. `需人工处理`：草稿存在，但仍有平台字段需要人工完成。

工具输出只能证明其实际返回的结果。无法查看目标草稿时，不能把封面、摘要、裁切效果和移动端呈现记录为已确认。

### 人工交接

每次投递后按字段报告：

```text
正文：
正文图片：
封面：
移动端呈现：
草稿状态：
公开发布：
人工处理：
```

存在草稿但结果不完整时，不自动重试。先让用户确认草稿状态，避免产生重复草稿。

## 文件改动

### `broadcast/SKILL.md`

在发布步骤后增加一条简短原则：投递完成后执行草稿落地验收，区分工具结果、实际确认结果和人工处理项。

### `broadcast/references/platform-wechat.md`

增加公众号移动端可渲染性检查，覆盖宽代码块、字符图、宽表格、封面和图片素材。

### `broadcast/references/publishing-wechatsync.md`

增加：

- 字段级适配器能力预检；
- 工具成功与草稿完整性的边界；
- 草稿落地状态；
- 人工交接模板；
- 不明确时不重试的约束。

不新增脚本和辅助文档，不把平台 API、登录和图片上传实现复制进 `broadcast`。

## 安全与授权

- 保持现有逐动作授权边界；
- 不读取或回显 Token、Cookie 和草稿凭据链接；
- 草稿保存不等于公开发布；
- 落地验收只使用已有安全入口或用户反馈，不绕过登录；
- 无法确认的字段明确标记为未确认。

## 验收标准

1. 遇到公众号宽代码块或字符图时，流程会在投递前要求移动端适配。
2. 发布入口接受 `--cover` 但适配器未应用时，不再报告“封面已上传”。
3. 草稿创建成功但封面缺失时，结果为“已保存草稿，需人工处理封面”。
4. 已存在草稿且状态不明时，不自动重复投递。
5. `broadcast/SKILL.md` 保持简洁，详细规则只进入对应参考文件。
