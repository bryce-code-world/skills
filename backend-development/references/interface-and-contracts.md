# 接口、RPC 与消息协议

S11 把已经通过实现可行性检查的交互目的转成可供各端独立开发、Mock、联调和验收的具体协议。

## 成熟度

| 状态 | 含义 |
| --- | --- |
| 草案 | S6 已确定场景、目的、调用方、Path 或消息形态及存量替换关系；责任服务和数据效果在 S10 闭合 |
| 待评审 | S10 已闭合方向性实现约束，具体协议和文档可供审阅 |
| 已冻结 | 评审问题已关闭，冻结版本已同步，依赖方可正式开发 |
| 已废弃 | 停止新调用，保留兼容期限、替代路径和历史追溯 |

## 设计协议

HTTP 和 RPC 定义路由或方法、请求、响应、字段语义、必填、空值、默认值、枚举、分页、排序、批量边界、错误码、幂等、并发和兼容策略。请求和响应优先直接使用与 source Proto 一致的结构块，注释、校验和字段号随结构表达；不要再用另一张表重复定义同一字段。公共结构只在公共对象文档定义。

WS、MQ、IM 定义触发场景、生产者、消费者、接收人、事件、载荷、顺序、去重、重试、失败处理和可观测证据。若同一业务同时存在 WebSocket 传输和消息表入库，必须分别说明外层封装、复用的消息体、表字段以及两者不复用的字段；消息参数可用字段路径表做业务绑定说明，但 Proto 结构仍是权威。

RPC 目录按服务分文件；每个服务文件再按其支撑的业务分章节，并在章节内区分不同 RPC。接口目录按服务加业务分文件或目录；消息协议按消息类型分文件，公共外层和公共对象单独放在 `00-公共约定与对象.md`。

使用 [api-contract.md](../assets/templates/api-contract.md)、[rpc-contract.md](../assets/templates/rpc-contract.md) 和 [message-contract.md](../assets/templates/message-contract.md)。

## 生成、评审和冻结

1. 按项目规则修改协议源文件并生成 OpenAPI、Swagger、Proto、RPC 方法文档或消息文档。协议文档必须记录每个接口/RPC/消息对应的 Proto 源文件路径；禁止手改生成物。
2. 补齐错误码、请求响应示例、消息示例和必要 Mock，标记“待评审”。
3. 在开发群同步权威入口、涉及模块、评审范围和反馈截止时间。
4. 在线回答普通字段、调用和场景问题；更新权威协议后重新生成并同步变化。
5. 只有范围较大、多端理解不一致、职责冲突或线上难以收敛时组织专项会议。
6. 问题关闭后标记“已冻结”，同步最终版本和变更点，前端及其他依赖方据此正式开发。

协议冻结前必须做一次逐项交叉核对，不能只确认方法名或路由存在：

- 确认该接口、RPC 或消息的权威源文件、文档版本、包路径和服务归属一致；
- 对 HTTP/RPC 请求响应核对字段名、类型、必填/空值、字段号、显式 `json_name`、枚举和错误语义；
- 对消息核对生产者、消费者、载荷、接收人、顺序、去重和失败处理；
- 核对新增、沿用、迭代和废弃状态，旧协议不能因仍存在于 source 就被误判为当前入口；
- 核对 HTTP 映射、生成物、Mock/示例和受影响测试均来自同一冻结版本；
- 文档与 source 冲突时，先确定当前对象的权威来源和人的取舍，不采用“全部以文档”或“全部以 Proto”的未经确认的全局规则；确认后同步另一侧并重新生成。

使用 [protocol-review.md](../assets/templates/protocol-review.md) 记录评审。

## 变更与废弃

冻结后变化先做影响检查。局部变化更新权威协议、重新生成并通知受影响方；改变需求、调用方范围或 S5 子业务流程时回退上游步骤。

废弃协议保留兼容期限、调用方迁移状态、替代路径和停止维护条件。接口实现是否保留由项目兼容策略决定；文档移入明确的废弃入口。
