# 存量文档迁移与规范化

`migrate` 只调整业务域文档的承载位置和导航，不代替 S1～S12 的业务设计与放行。

## 先确认迁移意图

区分两类任务：

- 原位复用：现有目录稳定，只建立 `P/S` 到权威路径的映射。
- 物理迁移：人已经确认目标目录、迁移范围、备份方式和引用修复边界。

目标业务域或目标仓库不能唯一确定时，只询问一个决定范围的问题。不得根据当前分支、最近提交或相邻目录猜测目标。

## 只记录迁移事实

材料是否找到、复用、迁移或完成核验，直接记录来源、目标、批次和证据，不建立全局材料状态枚举。

文件存在、目录完整和迁移完成都不等于业务结论已经确认或冻结。

## 执行迁移

1. 盘点来源文件、权威职责、目标路径、文件数量、内容哈希、引用和未决项。
2. 只为实际存在的职责记录六阶段和步骤映射。新建或确认重构业务域时，按实际交付物按需建立 `P1`～`P6` 和 `S1`～`S16` 路径，不为缺失步骤补空目录或完整词典。
3. 需要物理迁移时，先建立不可变备份或其他可恢复基线，再按已确认批次执行。
4. 迁移批次只允许复制或移动、建立导航、标记来源、修复路径变化造成的引用，并维护迁移状态。若经人确认调整步骤所属大阶段（例如将 S12 从 P4 归入 P5），必须同步根 README、Progress、阶段导航和所有相对链接；历史日志和只读备份不因现行目录编号调整而重命名或改写，确有现行反向引用时单独核对。
5. 保留原文中的 TODO、待确认、未完成和冲突。不得补业务规则、改数据结构、关闭问题或标记设计冻结。
6. 每批核对来源与目标数量、无需语义变化文件的哈希、TODO 数量、本地链接、UTF-8、LF 和实际 Git 差异；最终再扫描旧路径、旧文件名、旧编号和重复权威入口是否残留。
7. 全部批次完成完整性核验后，再从 P1 开始执行语义审查和阶段放行。

复杂迁移可以使用 [migration-plan.md](../assets/templates/migration-plan.md) 组织范围、批次和证据。计划默认放在对话或任务临时目录；只有它需要跨会话长期执行时才进入 `Progress.md`。

## 控制人工门禁

人一次确认完整迁移范围、目标拓扑和备份策略后，AI 可以连续执行其中确定性的迁移批次。

只有出现以下情况时暂停并重新确认：

- 目标职责或目录边界发生变化；
- 发现两个来源竞争同一权威位置；
- 必须改变业务语义才能继续；
- 需要扩大文件、仓库、删除或外部操作范围。

进度汇报不是人工放行门禁。不要让人对已确认范围内的机械迁移逐批重复批准。
