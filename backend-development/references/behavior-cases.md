# 行为验收案例

## 正向

| 输入 | 预期行为 |
| --- | --- |
| 产品评审后收到 PRD 和原型 | 完成启动准备，从 S1 建立业务模型初识，再进入 S2 梳理需求事实，不直接生成协议或代码 |
| 需求存在疑问 | S3 形成疑问清单，产品确认并回填 S2 和 S1 后再进入 S4 |
| 需要建立业务和数据模型 | S1 先收敛业务语义，S4 再设计数据承载 |
| S6、S7 已形成整体方案 | S8 先确认人数、期限和格式，再生成最小时间计划；S9 完成多端共识和计划沟通 |
| S10 发现工作包不合理 | 回到 S8 调整并完成必要沟通，再继续实现设计 |
| 前后端需要并行 | S11 生成具体协议并在线评审，冻结同步后各端开始正式开发 |
| 设计全部闭合 | S12 生成 `TASK-XX`、用例、追溯矩阵和业务 Review 清单 |
| 审查实现 | 独立 Reviewer 按任务级、工作包级和整体级执行四层 Review |
| 中断后继续 | 先读 `README.md` 理解业务域框架，再从 `Progress.md` 恢复迭代、`P`、`S`、`WP`、`TASK`、阻塞和下一步 |
| 人确认存量业务域整体规范化 | 进入 `migrate`，先固定备份、目标映射和批次；迁移只改变承载与引用，不推进 S1～S12 状态 |
| 当前步骤准备请求人放行 | AI 先完成上游逐项追溯，在对话中输出最小确认清单；不创建阶段评审文档 |
| S6 面向前端形成沟通材料 | 先固定读者与交付物契约，只写后端状态、错误、事件和调用要求，不替前端设计页面行为 |
| S7 面向前端整理接口与消息 | 按新增、旧接口迭代、停止调用及消息新增、沿用、不发送组织，不写内部编号和实现追溯 |
| S8 面向单人开发计划 | 默认生成一张顺序时间表，遵守人数和时间上限，不强制 `WP-XX`、里程碑和风险矩阵 |
| 新建或确认重构业务域 | 根目录生成 `README.md` 与 `Progress.md`；一级目录使用 `P{n}-业务化名称`；权威步骤目录或文档使用 `S{n}`，不复制完整 S1～S16 状态词典 |
| S9 有产品、项目、后端、前端和测试参加 | 按议题识别真实决策人、参与方和周知方，不建立五方逐项签字清单 |
| 文档所有者同时是后端负责人 | 复用其对当前基线的决定，不新增等待后端自我确认的问题 |
| 测试使用独立全量测试路径 | 只核对测试目标、可测试性、环境和联调依赖，不要求测试批准后端阶段计划 |
| 下午会议主要用于周知 | 由放行责任人决定是否接受后续调整风险；接受后记录非阻塞反馈和回退触发条件 |
| 冻结业务规则与当前代码不一致 | 保持冻结业务规则有效，把代码差异记录为 S10、S13 或 S14 实现缺口 |
| 当前存在三个待确认问题 | 展示剩余问题范围，但本轮只推进一个会改变下一步的确认点 |
| 当前工作切片或步骤已经完成 | 简述完成依据和下一步的目标、输入、产物，询问用户是否开始；未确认时停止 |

## 非触发

| 输入 | 预期行为 |
| --- | --- |
| 查询 Proto 枚举值 | 直接查询，不创建控制面 |
| 解释一段代码 | 只解释当前代码 |
| 修改一处明确文案 | 按最小修改执行，不补齐全部流程 |
| 用户只要 Review 结果 | 只读审查，不自动修复或重写设计 |

## 边界

| 情况 | 预期行为 |
| --- | --- |
| 存量目录稳定 | 建立六阶段和步骤映射，不搬迁 |
| 新建小型业务域 | 保留六个一级大阶段，内部平铺最少文档 |
| 大型业务域 | 一级大阶段稳定，内部按能力域、模块和维护责任拆分 |
| 四种类型无法表达 | 标记 `待识别类型`，由人决定是否扩展 |
| 两个并行迭代 | 分别维护位置和文件，不覆盖计划、Review 或验收记录 |
| 最小局部修改可闭合需求 | 采用最小正确实现；扩大治理前证明长期收益和可控成本 |
| 六阶段职责稳定但目录名不够业务化 | 保留 `P1`～`P6` 映射，允许人采用更清晰的实际目录名 |
| 大型业务域需要先固定完整骨架 | 经人确认后建立六个一级目录；导航写入 README，状态写入 Progress，不制造空设计正文 |
| 文档已经存在但没有评审证据 | 只记录材料事实，不据此把流程步骤标记为“待确认”“已确认”或“已冻结” |
| 人在放行摘要形成前回复“都正确” | 继续完成 AI 逐项审查，不把笼统确认解释为阶段放行 |
| 推荐依赖关联业务域口径 | 先核对目标域冻结需求和目标域现行实现；来源冲突时不提供确定性推荐 |
| 下游发现已冻结需求需要变化 | 在 `Progress.md` 记录待确认和影响范围；确认后直接更新权威正文，不创建单独 FC 文档 |
| 人已确认完整迁移范围 | 连续执行确定性迁移批次；只有边界、语义或授权变化时重新询问 |
| 大型业务域按模块组织 S1、S4 | 保留模块目录，在各权威文件名写入 `S1` 或 `S4`，不强制改成步骤优先目录树 |
| P1 企业权限和应用权限目录都只承载 S1 | 使用 `S1-01-企业权限`、`S1-02-应用权限` 二级目录，内部需求文件不重复 `S1` |
| 一个步骤存在多个同级交付物 | 使用 `S{n}-{两位序号}-名称`；已在 `S{n}` 目录内的普通子文档不重复步骤编号 |
| S3 没有独立永久文档 | 在 `Progress.md` 映射到开放事项和已回填需求事实、业务模型，不为显示 `S3` 创建空目录或过程文档 |
| S9 存在人工决策 | 先在对话中形成最小决策包，决定闭合后一次性回填；不先写永久问题清单再等待逐项纠正 |

## 失败

| 情况 | 预期行为 |
| --- | --- |
| 无法读取项目规则 | 停止，不猜测 |
| 无法确认业务域或仓库 | 只询问一个决定范围的关键问题 |
| 上游有阻塞决策 | 完成确定内容，阻塞下游步骤 |
| README/Progress 与事实冲突 | 报告差异，不声称完成 |
| 项目通用 Review 规范缺失 | 使用最低基线执行可执行部分，标记 `PROJECT_PROFILE_MISSING`，不判整体通过 |
| 无独立 Reviewer 或独立上下文 | 在 `Progress.md` 记录阻塞说明，S14 不标记为“已验证” |
| 单个 AI 任务仍然开放 | 退回 S12 继续拆分 |
| 协议缺少实现依据 | 不冻结，退回 S10 |
| 存量目录缺少步骤权威路径 | 记录缺失职责，不伪造路径或自动迁移 |
| README 只记录业务域框架 | 保持 README 精炼；从 `Progress.md` 恢复当前过程，不补齐完整 S1～S16 状态词典 |
| 用户未给出唯一业务域路径 | 只询问一个确定目标的问题，不根据分支、最近提交或相邻目录猜测 |
| 迁移过程中发现业务内容不完整 | 原样保留 TODO 和未决项，迁移完成后再进入对应流程步骤审查 |
| 会话在冻结结论回填中断 | 优先读取 `Progress.md` 的开放问题和当前工作区；没有稳定决定时不根据派生文档差异猜结论 |
| resume 检查点引用的路径已经不存在 | 废弃旧检查点路径，从当前 `Progress.md`、README 和 Git 状态重新发现权威入口 |
| 一个会话已经完成当前步骤 | 更新 `Progress.md` 并建议新开会话，不在同一长线程继续多个步骤 |
| 阶段审查需要核对代码现状 | 只核对会改变当前业务结论的事实；完整实现差异留到 S10 |
| 普通阶段审查考虑使用子任务 | 默认单 Agent；只有用户或宿主允许且证据方向独立时使用最小上下文子任务 |
| 只修改少量文档 | 只验证变更文件和受影响引用，不重复扫描整个业务域 |
| 一个步骤包含多个独立交付物 | 按交付物拆成工作切片，切片完成后更新 `Progress.md`，不在同一会话继续下一切片 |
| 切片完成后用户没有确认继续 | 只保留续跑检查点，不读取或执行下一切片 |
| 用户坚持在当前长线程继续 | 先说明同一线程无法消除历史上下文 Token，再按显式覆盖继续当前切片 |
| 同一文档连续收到修改意见 | 视为同一审阅任务，用户确认完成或进入下一切片后再统一验证、提交和写日志 |
| 前端流程图横向过长或节点文字被截断 | 改用单主题纵向图，保留 `START[流程主题]` 和实际 Path；仍过长时拆图并执行视觉验收 |
| S8 压缩计划格式 | 只压缩载体，不合并 S5 中需要独立实施的业务流程 |
| 当前发现属于缓存、事务、RPC 或协议字段 | 记录为技术后置，分别留到 S10 或 S11，不回填 P1，除非改变产品可观察行为 |
