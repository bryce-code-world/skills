# 行为验收案例

## 正向

| 输入 | 预期行为 |
| --- | --- |
| 产品评审后收到 PRD 和原型 | 完成启动准备，从 S1 梳理需求事实，不直接生成模型、协议或代码 |
| 需求存在疑问 | S2 形成疑问清单，产品确认并回填后再进入 S3 |
| 需要建立业务和数据模型 | S3 先固定业务语义，S4 再设计数据承载 |
| S6、S7 已形成整体方案 | S8 生成带 `WP-XX` 的项目计划，S9 完成多端共识和计划沟通 |
| S10 发现工作包不合理 | 回到 S8 调整并完成必要沟通，再继续实现设计 |
| 前后端需要并行 | S11 生成具体协议并在线评审，冻结同步后各端开始正式开发 |
| 设计全部闭合 | S12 生成 `TASK-XX`、用例、追溯矩阵和业务 Review 清单 |
| 审查实现 | 独立 Reviewer 按任务级、工作包级和整体级执行四层 Review |
| 中断后继续 | 从控制入口恢复迭代、`P`、`S`、`WP`、`TASK`、阻塞和下一步 |
| 人确认存量业务域整体规范化 | 进入 `migrate`，先固定备份、目标映射和批次；迁移只改变承载与引用，不推进 S1～S12 状态 |
| 当前步骤准备请求人放行 | AI 先完成上游逐项追溯并输出阶段评审包，人只确认冲突和真实业务决策 |

## 非触发

| 输入 | 预期行为 |
| --- | --- |
| 查询 Proto 枚举值 | 直接查询，不创建控制面 |
| 解释一段代码 | 只解释当前代码 |
| 修改一处明确文案 | 按最小修改执行，不补齐全部流程 |
| 用户只要 Review 结果 | 只读审查，不自动修复或重写设计 |

## 边界

| 情况 | 预期行为 |
| --- | --- |
| 存量目录稳定 | 建立六阶段和步骤映射，不搬迁 |
| 新建小型业务域 | 保留六个一级大阶段，内部平铺最少文档 |
| 大型业务域 | 一级大阶段稳定，内部按能力域、模块和维护责任拆分 |
| 四种类型无法表达 | 标记 `待识别类型`，由人决定是否扩展 |
| 两个并行迭代 | 分别维护位置和文件，不覆盖计划、Review 或验收记录 |
| 最小局部修改可闭合需求 | 采用最小正确实现；扩大治理前证明长期收益和可控成本 |
| 六阶段职责稳定但目录名不够业务化 | 保留 `P1`～`P6` 映射，允许人采用更清晰的实际目录名 |
| 大型业务域需要先固定完整骨架 | 经人确认后建立六个一级导航和状态入口，不制造空设计正文 |
| 文档已经存在但没有评审证据 | 只更新材料状态，不据此把流程步骤标记为 `REVIEW_READY` 或 `FROZEN` |
| 人在评审包形成前回复“都正确” | 继续完成 AI 逐项审查，不把笼统确认解释为阶段放行 |
| 推荐依赖关联业务域口径 | 先核对目标域冻结需求和目标域现行实现；来源冲突时不提供确定性推荐 |
| 下游发现已冻结需求需要变化 | 先记录冻结变更和人的决定，将上游标为 `CHANGE_PENDING`，再按影响顺序更新和重新放行 |
| 人已确认完整迁移范围 | 连续执行确定性迁移批次；只有边界、语义或授权变化时重新询问 |

## 失败

| 情况 | 预期行为 |
| --- | --- |
| 无法读取项目规则 | 停止，不猜测 |
| 无法确认业务域或仓库 | 只询问一个决定范围的关键问题 |
| 上游有阻塞决策 | 完成确定内容，阻塞下游步骤 |
| 控制入口与事实冲突 | 报告差异，不声称完成 |
| 项目通用 Review 规范缺失 | 使用最低基线执行可执行部分，标记 `PROJECT_PROFILE_MISSING`，不判整体通过 |
| 无独立 Reviewer 或独立上下文 | S14 标记 `BLOCKED` |
| 单个 AI 任务仍然开放 | 退回 S12 继续拆分 |
| 协议缺少实现依据 | 不冻结，退回 S10 |
| 存量目录缺少步骤权威路径 | 记录缺失职责，不伪造路径或自动迁移 |
| 用户未给出唯一业务域路径 | 只询问一个确定目标的问题，不根据分支、最近提交或相邻目录猜测 |
| 迁移过程中发现业务内容不完整 | 原样保留 TODO 和未决项，迁移完成后再进入对应流程步骤审查 |
| 会话在冻结结论回填中断 | 优先读取确认记录或冻结变更记录；没有稳定决策记录时不根据派生文档差异猜结论 |
