# Bug 与持续反馈

优先遵守目标项目 Bug 规范。本文件只规定 Bug 怎样反馈到业务域研发体系。

## 处理顺序

1. 固定现象、请求、环境、影响范围和期望行为。
2. 从真实入口追踪代码、协议、数据、日志和运行证据，定位共享根因。
3. 按项目规则建立回归用例并完成最小正确修复。
4. 记录实际差异、验证证据、剩余风险和回滚方式。
5. 判断根因反馈到哪个长期载体。

使用 [bug-feedback.md](../assets/templates/bug-feedback.md)。

## 反馈层级

- 业务模型、需求事实或确认冲突：回到 S1～S3。
- 数据模型错误：回到 S4。
- 流程或调用方责任缺失：回到 S5～S7。
- 协议语义不完整：回到 S11。
- 实现偏差：保留在 Bug、测试和 Review 记录，不改写正确设计。
- 测试或 Review 漏洞：更新回归测试、项目 Review 规范或业务 Review 清单。
- 运行观测不足：更新日志、指标、告警或数据健康检查。

只有改变长期有效结论时才修改业务设计。不得只修复代码后关闭记录。

## 迭代反馈

Bug 属于当前迭代时链接对应 `TASK-XX`、Review 和验收记录。跨迭代长期问题进入明确后续迭代或观察清单。

迭代完成后按 [iteration-lifecycle.md](iteration-lifecycle.md) 关闭并建立历史索引。
