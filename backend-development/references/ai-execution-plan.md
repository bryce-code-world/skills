# AI 执行计划

S12 把工作包实现设计和冻结协议转成可逐项独立执行、验证、Review 和续跑的任务。S12 属于 P5，承接 P4 已完成的实现设计与协议冻结。

## 建立执行基线

1. 建立需求点到业务模型、数据模型、S5 子业务与流程、调用方流程、协议、实现和测试的追溯矩阵。
2. 建立正常、异常、边界、权限、并发、依赖失败、迁移和回滚用例。
3. 建立一个唯一的任务登记与依赖入口；按 `WP-XX` 分组，再按真实技术依赖排列任务。不要创建 `WP-00` 任务表或其他重复登记表。
4. 为当前业务生成任务级、工作包级和整体级 Review 清单。

使用 [traceability-matrix.md](../assets/templates/traceability-matrix.md) 和 [business-review-checklist.md](../assets/templates/business-review-checklist.md)。

## 拆分 `TASK-XX`

每个任务只实现一个可验证业务行为，并且只绑定一个清晰、可独立交付的责任单元或明确的调用适配层。责任单元按项目架构确定：微服务可以是服务，单体可以是模块、组件或分层，必要时也可以是独立生成物或客户端适配层。跨责任单元业务通过 TASK 依赖链串联，不把多个责任单元塞进同一个任务。若代码在技术上不可分割，必须说明稳定责任边界、不可拆分原因和验证方式，不得用架构名称替代边界判断。共享缓存协议、协议生成和 clients 适配层必须在任务基线中明确其冻结来源与责任归属。每个任务固定：

责任单元不是颗粒度终点。同一责任单元内若存在多个 HTTP/RPC/消息消费/定时任务/命令入口，或多个可以独立验收的状态闭环，继续拆成不同 TASK；每个 TASK 原则上只登记一个主入口或一个闭环。只有技术上不可分割时才允许合并，并写明不可分割原因、共同验证方式和失败归因。共享 helper 只有在确实服务同一闭环且不扩大边界时随任务修改，否则独立成任务并建立依赖。

- 目标行为和预期结果；
- 所属迭代、`WP-XX` 和任务标识；
- 责任单元或调用适配层；
- 前置任务和权威设计；
- 涉及仓库、责任单元、允许修改文件和禁止事项；同一 TASK 不得无说明地跨多个责任单元或跨仓库；
- 输入、异常、权限、并发和依赖失败边界；
- 主入口/闭环、业务目的、下游消费者和持久化状态（pending/outbox 等）的生产者、消费者、重试触发与终态；
- 失败验证命令、通过标准、回归范围和 Review 检查点；
- Git、环境和外部沟通授权；
- 断点续跑、阻塞和止损条件。

`TASK-XX` 的唯一编号、状态、依赖和当前门禁以任务登记与依赖入口为准；任务正文只保留该任务的执行设计和证据。公共门禁任务可以使用 `TASK-00`，但不填写虚构的 WP 归属。

Proto、生成物和 `clients` 适配层必须明确各自责任单元/TASK；如果生成流程天然跨目录，仍需指定唯一责任边界、允许修改范围和独立验证命令，不得用“基础设施”掩盖多个责任单元混合。

生成的 model、query、Wire 或其他代码生成物只能由已确认的源文件、Schema/DDL 和既有生成流程产生；不得手写或顺手新增生成模型。新增表、字段、持久化状态或 outbox 必须先有 S4 数据模型、迁移/DDL 和相应授权，不能为了补偿、重试或可靠性窗口临时扩展数据层。

已完成任务不应被静默改写。只有在用户明确确认编号重排时，才可将未开始或当前计划任务重新连续编号；同步更新唯一登记表、WP 任务表、Progress、S10 引用和依赖，并保留历史编号映射或日志说明。

任务仍需跨多个开放业务边界、无法独立验证或需要 AI 自行补充业务决定时继续拆分，不进入 S13。

使用 [ai-execution-plan.md](../assets/templates/ai-execution-plan.md)。

## 执行规则

S13 一次只执行一个 `TASK-XX`。先重新读取项目规则和任务引用，再按项目测试与实现流程完成开发、验证和差异检查。

任务完成后使用 [task-execution-record.md](../assets/templates/task-execution-record.md) 记录实际差异、命令、证据、未验证项和下一任务。不得借实现、测试或重构扩大范围。

如果迁移或重排 S12 目录，必须同步更新 `README.md`、`Progress.md`、阶段导航和所有相对链接，并扫描旧 P4/S12 路径、旧 WP 编号和重复 TASK 入口是否残留。
