# 需求事实与确认

## S1：需求事实梳理

输入是产品评审后的 PRD、原型、评审结论和补充材料。先记录版本与来源，再按业务模块逐项梳理：

- 需求边界、目标和明确非目标；
- 角色、权限主体和使用场景；
- 用户操作、系统行为和预期结果；
- 业务规则、状态、异常和验收口径；
- 前端、移动端、内部服务、第三方或无前端场景；
- 与存量实现、协议和数据的已知关系；
- 原文没有回答的疑问。

每个需求点分配稳定编号并链接来源。产品目标、现有实现和设计推导分开记录。

使用 [requirement-facts.md](../assets/templates/requirement-facts.md)。

## S2：需求确认沟通

将疑问按影响分类：

- 阻塞业务模型；
- 阻塞数据模型；
- 阻塞整体流程或多端交互；
- 可在具体协议或实现阶段确认；
- 不属于本次范围。

确认记录写明问题、上下文、可选口径、产品结论、受影响需求点和回填位置。不能用会议纪要替代权威需求事实；确认后必须回填 S1。

使用 [requirement-confirmation.md](../assets/templates/requirement-confirmation.md)。

## 退出检查

- 每个需求点能追溯到输入来源或明确的确认结论。
- 阻塞 S3 的疑问已经关闭。
- 未决项有责任人、影响步骤和最晚确认点。
- 不以现有表、接口或代码结构替代业务需求。
