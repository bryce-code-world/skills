# 整体方案共识与计划沟通

S9 同时完成两件事：确认 S6 协议清单与 S7 调用方对接说明构成的整体方案，并与项目负责人确认 S8 项目开发计划。

## 会前材料

- S6 协议清单；
- S7 前端与其他调用方对接说明；
- S8 项目开发计划；
- 尚未关闭的产品交互疑问和已知风险。

## 先确定决策责任

产品、项目、后端、前端或其他主要调用方、测试可以参加，但参加不等于拥有放行权。

对每个议题分别识别：

- 决策人：有权决定该议题结论的人；
- 参与方：提供事实或共同理解方案的人；
- 周知方：只需知道结论和影响的人。

同一人兼任多个角色时只记录一次真实决定，不建立自我确认任务。测试只确认测试目标、可测试性、环境和联调依赖，不默认审批后端阶段拆分或开发时间表。

## 区分沟通影响

每项沟通使用以下一种类型：

- 阻塞决定：缺少结论会改变产品范围、调用方职责、S5 子业务流程、项目计划或验收口径。未关闭时阻塞 S9。
- 非阻塞反馈：当前基线可执行，放行责任人接受后续调整成本。记录反馈范围和触发回退的条件后可以继续。
- 纯周知：只负责周知，不参与 S9 放行。

以上是 S9 的议题分类，不是研发流程状态。

参与方未反馈不能自动推导为阻塞决定。

只有真实决策人缺失，或者缺失结论会改变当前基线时，才标记阻塞。

## 先收敛再写入

1. 只读核对 S6、S7、S8、`README.md`、`Progress.md` 和冻结需求。
2. 删除已经由冻结事实回答的问题，把现行实现偏差留给 S10、S13 或 S14。
3. 在对话中提交最小决策包，只列阻塞决定和需要人接受的风险。
4. 每轮只推进一个决定或风险接受点，等待回答后再进入下一个沟通点。
5. 取得决定后再回填 S6、S7、S8 和 `Progress.md`。
6. 项目需要保留正式会议结论、风险接受或跨团队基线时，才使用 [solution-consensus-record.md](../assets/templates/solution-consensus-record.md)。

新发现的产品疑问由产品确认。无法当场确认且会改变整体方案时回到 S3，确认后回填 S2 和 S1，再更新 S6、S7、S8 并重新检查受影响结论。

## 沟通边界

S9 形成多端共识基线，不逐字段冻结具体协议。S11 的普通字段和调用问题默认在线评审；只有范围较大、多端理解不一致、职责冲突或线上难以收敛时再开专项会议。

## 退出检查

- 阻塞决定已由真实决策人关闭。
- 非阻塞反馈已记录风险接受人、反馈范围和回退触发条件。
- 纯周知已明确周知对象和当前基线，不等待逐方签字。
- 会改变当前基线的产品疑问已关闭；其他产品反馈已经分类为非阻塞反馈或纯周知。
- 项目负责人已确认 S8 计划阶段、时间和协作点；项目计划使用 `WP-XX` 时同时确认其边界。
- 结论已回填权威文档，沟通记录不替代权威设计。
