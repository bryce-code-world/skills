# 流程步骤状态机

## 使用方式

先从控制入口恢复当前位置，再执行对应流程步骤。

设计模式一次只推进一个工作切片。大型步骤按业务模块、流程簇、交付物或问题批次拆分，切片状态只记录在控制入口，不新增永久过程文档。

每轮沟通只推进一个可确认点。需要多个人工决定时可以列出剩余项，但每轮只请求一个会改变下一步的回答。

当前步骤全部切片完成前保持 `IN_PROGRESS` 或 `BLOCKED`；全部切片审查完成后才进入 `REVIEW_READY`。

存量文档迁移不属于 S1～S16。

用户确认完整迁移范围后，可以按 [migration-and-normalization.md](migration-and-normalization.md) 连续执行多个确定性批次。不得把迁移完成当成设计放行。

## 六个研发大阶段

| 研发大阶段 | 步骤 | 目标 |
| --- | --- | --- |
| P1 需求事实与确认 | S1～S2 | 把产品输入转成经过确认、可以落地的需求事实 |
| P2 业务建模与流程设计 | S3～S5 | 建立业务语义、数据承载和端到端流程 |
| P3 多端协同与方案共识 | S6～S9 | 明确调用方工作、交互目的、项目计划并达成多端共识 |
| P4 详细技术设计与 AI 执行计划 | S10～S12 | 完成工作包实现设计、协议冻结和细粒度任务计划 |
| P5 AI 执行、Review 与交付 | S13～S15 | 实现、独立审查、联调、验收和交付 |
| P6 持续反馈与演进 | S16 | 将 Bug 和迭代发现反馈到长期研发体系 |

## 步骤契约

| 步骤 | 进入条件 | 核心动作 | 权威交付物 | 退出条件 |
| --- | --- | --- | --- | --- |
| 启动准备 | 已取得任务；目标路径可唯一确定 | 读项目规则；确认仓库、授权、事实源；建立或恢复控制入口；形成初步业务域画像 | 控制入口、目录映射、事实来源清单 | 能确定业务域、写入边界和 S1 入口 |
| S1 需求事实梳理 | PRD、原型或其他产品输入可定位 | 按模块逐项提取范围、角色、场景、规则、异常、验收和来源 | 需求事实、需求点清单、疑问清单 | 每个需求点可追溯，未知没有伪装成事实 |
| S2 需求确认沟通 | S1 已形成疑问清单 | 与产品确认阻塞疑问，直接回填受影响需求并关闭控制入口开放项 | 确认后的需求事实、控制入口开放项；项目要求时补正式确认记录 | 阻塞模型设计的疑问关闭 |
| S3 业务模型 | S2 已放行 | 定义对象、角色、关系、能力、规则、不变量、状态和生命周期 | 业务模型及需求映射 | 数据模型不需要猜测业务语义 |
| S4 数据模型 | S3 已放行 | 定义数据归属、持久化模型、运行时模型、约束、迁移和数据健康 | 数据模型及业务映射 | 能表达业务规则和生命周期 |
| S5 整体流程框架 | S3、S4 已放行 | 按业务场景贯通责任方、权威状态、成功结果和失败业务效果；技术实现细节留 S10 | 整体流程、关键子流程、最终业务域画像 | 主流程、跨域触发和异常业务结果可追溯 |
| S6 调用方范围与视角流程 | S5 已放行 | 明确后端向前端、内部服务、第三方和无前端场景提供的状态、错误、事件和调用时机，不替调用方设计 UI | 调用方范围、视角流程、联调场景 | 各调用方知道后端提供什么、何时调用和怎样感知业务结果 |
| S7 交互目的清单 | S6 已放行 | 按调用方阅读任务整理新增、迭代、沿用和停止调用的 HTTP、RPC、WS、MQ、IM 能力；协议细节留 S11 | 面向调用方的接口与消息清单 | 每项交互覆盖实际业务动作和替换关系，没有混入实现细节 |
| S8 项目开发计划 | S5～S7 已放行 | 先确认人数、期限和格式，再按独立流程、模块和依赖形成最小时间计划；`WP-XX` 可选 | 项目开发计划草案 | 项目负责人可以按已确认约束排期和跟踪 |
| S9 整体方案共识与计划沟通 | S6～S8 草案完整 | 按议题识别决策人、参与方和周知方，区分阻塞决定、非阻塞反馈和纯周知，再确认方案和计划 | 权威正文回填、确认后的计划；需要正式留痕时补共识记录 | 阻塞决定已关闭，计划已与项目负责人对齐，非阻塞反馈有风险接受人与回退条件 |
| S10 工作包实现设计 | S8、S9 已放行 | 按 S8 计划阶段建立或复用内部 `WP-XX`，再设计数据使用、事务、依赖、中间件、生命周期、代码组织、测试和回滚 | 每个工作包的实现设计 | 会改变外部协议的实现约束已闭合 |
| S11 协议设计与冻结 | S7、S9、S10 已放行 | 定义并生成 HTTP、RPC、消息协议；线上评审；必要时专项会议；冻结并同步 | 冻结协议、错误码、Mock、评审记录 | 各端可基于同一版本独立开发和验证 |
| S12 AI 执行计划 | S10、S11 已放行 | 建立用例、追溯矩阵和 Review 清单；按工作包拆成 `TASK-XX` | AI 执行计划、验收命令、业务 Review 清单 | 单任务无需新增业务假设即可执行 |
| S13 逐任务开发与验证 | 当前任务已放行 | 按项目规则和单个行为切片实现、测试、回归并记录差异 | 代码、测试、生成物、验证记录 | 当前任务达到 `IMPLEMENTED` 并可独立 Review |
| S14 独立 Review、修复与复审 | 存在可审查差异 | 按任务级、工作包级、整体级执行项目、业务、风险和证据 Review | Review 报告、修复和复审证据 | 当前颗粒度问题已关闭或由人接受风险 |
| S15 联调、验收与交付 | 全部任务和 Review 收敛 | 联调、验收、上线准备、回滚和交付核对 | 验收报告、交付证据、未验证项 | 项目交付口径满足，迭代可关闭 |
| S16 Bug 与迭代反馈 | 出现缺陷或迭代关闭 | 修复缺陷，更新测试、Review 或长期权威设计，关闭迭代 | Bug 闭环、设计增量、历史索引 | 影响已反馈到正确长期载体 |

## 阶段放行

当前工作切片结束时，AI 在对话中按以下类型整理发现：

- `FACT_FIX`：权威事实唯一确定，AI 直接修复；
- `BUSINESS_DECISION`：改变业务结果、范围或验收，交给人决定；
- `TECH_DEFERRED`：属于后续技术或协议步骤，当前只登记影响；
- `OUT_OF_SCOPE`：不属于当前业务域、当前调用方或当前迭代。

只有当前步骤全部切片完成后，才汇总仍开放的 `BUSINESS_DECISION` 并申请进入 `REVIEW_READY`。

不得要求人通读整批文档自行找错。人在放行摘要形成前给出的“正确”“继续”等笼统确认，只表示允许继续审查，不能直接将步骤改为 `FROZEN`。

人的放行必须对应已经展示的问题清单和当前内容基线。放行摘要只服务当前确认，不写入业务域目录。

当前工作切片或流程步骤完成后，先简要说明完成依据和下一步的目标、输入、产物，再询问用户是否开始。没有明确确认时停止，不自动进入下一对象。

`FROZEN` 可以同时存在已记录的 `NON_BLOCKING_FEEDBACK` 和接受风险，但不能存在未关闭的 `BLOCKING_DECISION`。

会议参与者未反馈、纯周知未完成或同一人的自我确认不构成阻塞。

## 受控回退

发现缺口时回到最早需要重新决定的步骤：

- 需求或产品交互不清：S2。
- 业务对象、规则或状态不成立：S3。
- 表达、归属、迁移或数据健康不成立：S4。
- 端到端流程断裂：S5。
- 调用方职责或感知流程不清：S6。
- 交互目的或存量迁移不完整：S7。
- 工作包、依赖、里程碑或风险不完整：S8，并完成必要的 S9 计划沟通。
- 实现约束不可行：S10。
- 协议字段、错误、兼容或消息语义不完整：S11。
- AI 任务仍然开放或不可独立验证：S12。

回退涉及已冻结结论时，先将最早受影响步骤改为 `CHANGE_PENDING`，并在控制入口记录开放问题、原冻结基线和影响范围。

人的决定确认后，直接更新权威正文，再按上游到下游顺序复核和重新放行。技术选择只有改变用户可观察行为、产品范围或验收口径时才回退需求步骤；其余留在 S4、S10 或 S11。关闭后的过程不建立独立冻结变更文档。

回退时记录原因、受影响产物、需要重新验证的对象和重新放行人。
