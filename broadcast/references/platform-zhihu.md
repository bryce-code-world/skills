## 输入契约

开始前确认：

- 一篇明确的权威内部底稿已经通过底稿门禁；
- `00-广播任务总结.md` 已经生成且没有复述底稿；
- 主风格、本平台侧重点和本次特别要求可用；
- 目标是知乎独立文章。

底稿不完整时停止或转交 `$lightning`；任务总结缺失时先补任务总结。不得读取其他平台稿补造核心内容。

## 重构目标

知乎文章面向独立议题、机制解释和长期检索。重构重点是让命题清楚、推理可跟随、反对意见和边界可见，同时保持普通读者能够进入。

可以调整：

- 将标题改为清楚、可检索的问题、判断或阅读收益；
- 开头直接提出命题及其现实意义；
- 提高概念、推理和证据的显性程度；
- 将已有反例、限制和误解移动到对应论断附近；
- 根据知乎阅读任务重新展开底稿中的解释、证据和反方观点；
- 压缩只服务公众号关系语境的铺垫和转场；
- 结尾交付可复用的框架或判断。

保留作者提出问题、修正判断和做出取舍的过程，但个人表达服务于论证，不能替代证据。

不得新增底稿中不存在的事实、案例、经历、核心观点和第二主线。需要的论证不在底稿时，缩小表达或停止并请求补充底稿。

## 入口传播组合

知乎入口首先要让读者判断这个命题是否值得理解和长期检索。标题、封面和开头共同建立问题范围、判断增量和论证预期。全文设计同时读取 [opening-engineering.md](opening-engineering.md)、[body-engineering.md](body-engineering.md) 和 [ending-engineering.md](ending-engineering.md)。

- 标题：形成准确、独立且可检索的问题或判断，让读者知道文章比常识多解释什么；
- 封面：强化议题对象和认知冲突，不伪装成真实新闻事件，不把有限判断画成普遍定律；
- 开头：立即提出核心命题、现实意义和文章准备解决的关键误解；
- 正文：用概念、理由、证据、反方和边界兑现判断增量；
- 结尾：交付可复用判断框架，不以点赞、关注或站队代替结论。

写正文前确定标题假设、封面信息任务和开头任务；成稿后联动校准。标题提出的问题、封面制造的冲突和正文实际论证必须处于同一事实强度。

## 阅读节奏

优先采用：

1. 标题形成一个可以独立成立的命题。
2. 开头较快给出核心判断和为什么值得理解。
3. 首次出现专业概念时给出通俗入口和准确含义。
4. 正文按概念、判断、证据、推理和应用推进。
5. 主动处理最可能的反驳、限制、误解和适用边界。
6. 数据、来源名称和作者判断贴近对应论断，不在文末集中列参考资料。
7. 结尾提供读者能够复用的判断框架，不强制点赞、关注或互动。

每个核心命题至少交代判断、理由、可能的反对意见和适用边界。知乎允许较高信息密度，但不能用术语堆叠代替解释，也不能用权威口吻代替来源和推理。

## Markdown 产物

输出 `02-知乎文章.md`，使用带结构的 Markdown。标题结构必须遵守 [platform-markdown-contract.md](platform-markdown-contract.md)：front matter 的 `title` 是唯一发布标题，正文不再包含 H1，而是直接从导语开始。当前环境已有等价明确协议时可以映射为该协议：

```markdown
---
platform: zhihu
title: "推荐标题"
summary: "文章摘要"
cover: "assets/zhihu/cover.png"
source: "<权威内部底稿路径>"
---

正文……

![准确的替代文字](assets/shared/example.png)

图注……
```

如果当前发布入口使用其他元数据协议，在投递阶段映射字段，不把发布参数写进正文。Markdown 是内容真相源，不能依赖下游删除重复标题；正文小标题从 `##` 开始。知乎编辑器中的呈现是下游渲染结果。

正文格式可以使用：

- 标题层级；
- 自然段；
- 列表；
- 少量强调；
- 链接、图片和图注。

读取 [platform-format-contract.md](platform-format-contract.md)，优先使用知乎原生标题、列表、图片和少量强调。通常不手写目录，不用公众号式色块或复杂自定义 HTML。

## 公开正文硬限制

知乎成稿不得出现：

- 三个反引号或三个波浪线形成的围栏代码块，包括用来排版普通文字的 `text` 代码块；
- 以 `>` 开头的 Markdown 引用块；
- Markdown 表格、ASCII 图、空格对齐的多列文本和 `<pre>` 等不自动换行结构；
- 作为独立可见文本的长网址、长路径、长命令和连续标识符；
- “参考资料”“参考文献”“资料来源”“来源列表”等文末章节；
- 脚注、尾注和编号链接列表。
- 正文一级标题，或在正文首行重复 front matter 的标题。

对照内容改为分点列表或常见阅读宽度下可读的纵向信息图。需要保留原话或重点结论时写成自然段，必要时使用少量加粗。必须说明出处时，在相关句子中自然写明来源名称，并把链接附在简短名称上。完整来源、素材授权和风险信息只写入 `05-验收报告.md`。

## 视觉处理

- 复用直接来自底稿、且至少两个平台都需要的共享正文插图；
- 按 [orchestration.md](orchestration.md) 的视觉路由生成知乎封面和必要裁切版本：概念型、编辑型封面优先 `$canvas-design`，既定方向需要照片、复杂插画或纹理位图时使用 `$imagegen`；
- 根据论证顺序调整插图位置，不改变图片语义；
- 保证图片文字在常见阅读宽度下清楚；
- 保留封面的设计说明或可编辑源文件，以及最终 PNG；
- 实际查看渲染结果并完成至少一次视觉批评和修正；
- 不用封面或图注把有限结论扩大为普遍定律。

## 交付与验收

交付：

```text
02-知乎文章.md
assets/zhihu/
```

检查：

- 只看标题和封面时，目标读者是否能识别准确命题、问题范围和阅读增量；
- 受众认知层级是否在写作前明确，入口、术语密度和解释深度是否与该层级一致；
- 标题、封面、开头和正文是否兑现同一入口承诺，结尾是否固化同一主要目标效果；
- 开头是否通过第一屏门，正文是否通过推进门，结尾是否通过最后一屏门；
- 开头是否快速给出判断和阅读价值；
- 结论是否有推理、来源或明确的作者判断支撑；
- 事实、推断和观点是否清楚区分；
- 边界、反例和可能争议是否得到处理；
- 是否形成“判断—理由—可能的反对意见—适用边界”的有效闭环；
- 是否保留底稿的事实、观点强度和适用边界；
- 是否保留作者真实的提问和判断修正过程，又没有让个人表达替代证据；
- 是否完全不存在围栏代码块、引用块、Markdown 表格、ASCII 排版和横向滚动结构；
- front matter 是否包含唯一发布标题，正文是否从导语开始且不存在 H1；
- 是否没有参考资料、参考文献、资料来源、脚注、尾注和编号链接列表；
- 是否优先使用平台原生结构，没有手写重复目录和公众号式富文本装饰；
- 是否与其他已生成平台版本形成真实语境差异；
- 共享插图、封面和适配素材是否完整；
- 是否没有新增内部底稿之外的实质内容；
- 是否由独立读者完成五道门禁和正文未出现过的陌生场景迁移题，并在 `06-读者测试.md` 留下问题证据、判断过程、修改动作和复测结论；只有作者自检时不得标记为通过。
