# 闪电

把内部文档整理成自己能快速理解、AI 能立即行动的形式。

## 遵守质量优先级

按以下顺序处理，后面的目标不能破坏前面的目标：

1. 关键信息完整。
2. 事实准确。
3. 定义与边界无歧义。
4. 推理成立，句间关系清楚。
5. 语句通顺，容易理解。
6. 表达简洁。
7. 形式美观。

压缩表达，不压缩事实，也不压缩理解事实所需的逻辑关系。

## 维护版本与依赖

每次触发时读取 [dependencies.md](references/dependencies.md)，按其中的 24 小时规则执行非阻塞自身更新检查。

更新检查失败或发现新版本时，继续使用当前版本完成文档任务；只在交付时报告，不让检查中断当前工作。

只有当前任务确实需要外部 Skill 时才检查对应依赖。缺失时先说明并等待一次安装确认，不预装全部可选能力。

## 执行工作流

1. 读取原始材料、目标文件和适用的项目规则。
2. 识别文档类型、主要阅读任务、目标读者已有知识、范围、事实来源和目标环境。
3. 建立内部来源账本，不默认输出这份账本。
4. 判断原文是否已经足够清楚；足够清楚时保持不变。
5. 标记未知、冲突和缺失前提，不自行补全。
6. 概念、认知、边界类文档或跨章节重组任务，读取 [reader-continuity.md](references/reader-continuity.md)，建立概念依赖和内容角色。
7. 先建立由内容关系决定的最小骨架，再把信息点放入对应位置。
8. 选择短句、分点、表格、图示、附录或链接。
9. 创建或修改文档，先检查推理和句间关系，再删除重复、简化语言。
10. 将成稿逐项回对来源账本。
11. 只依据最终文档完成冷读和自检。

主要阅读任务只能有一个：

- 理解。
- 决定。
- 执行。
- 查询、记录或跟踪。

## 保留关键信息

在来源账本中逐项记录：

- 结论、定义、规则、动作和验收。
- 名称、术语、路径、表名、字段名和枚举显示值。
- 数字、单位、时间范围、顺序、条件、例外和失败路径。
- 不同版本、备选方案、观点归属及其确认状态。
- “可能”“建议”“暂定”“已经确认”等语气强度。

材料包含多轮讨论或多个版本时，按语义维度逐项枚举，不抽取“代表版本”代替完整记录。

重点检查：

- 结构和目录的每个版本。
- 分类、清单和步骤的每个版本。
- 数量、范围和时间口径的每个版本。
- 流程、层级、因果和依赖关系的每个版本。
- 同一概念的不同定义及其冲突。

优先保留：

- 结论和定义。
- 前置条件与约束。
- 例外和失败路径。
- 动作与验收标准。

将必要证据、推导、实现细节和历史记录放入附录或独立文档。

删除内容前，确认它是重复表达，不是独立事实。

来源账本中的每一项都必须满足以下一种结果：

- 在正文中准确保留。
- 移入可访问的附录或权威链接。
- 作为未决项或冲突明确标记。

不得静默省略。

不要用近义词替换名称、清单项、步骤名、分类名和约束词。

使用附录或链接承接省略内容时，确保目标文件真实存在且会持续保留。

修改原文件时，不要把“修改前的原文件”当作修改后的权威链接。

如果没有可持续访问的来源文件，就在当前文档中保留完整事实。

成稿前建立“来源项 → 成稿位置或去向”的对应关系。

只有每个来源项都有明确去向，信息核对才算完成。

## 处理未知与冲突

先完成所有确定内容。

区分用户确认、来源事实、他人建议和编辑新增。

不要因为某个方案最后出现，就把它当作已经确认的最终方案。

原文包含多个目录、分类、时间口径、数量或框架版本时，逐项保留差异。

整理对话记录或多轮方案时，增加紧凑的“版本与采用状态”记录。

至少记录：

- 议题。
- 各版本或观点。
- 可核验的来源位置。
- 内容性质。
- 采用状态。

不要把来源、内容性质和采用状态混在同一列。

内容性质至少区分：

- 用户陈述。
- 来源事实。
- 他人建议。
- 编辑新增或推断。

采用状态使用含义明确且前后一致的词，例如：

- 已确认。
- 未确认。
- 暂不采用。
- 冲突待确认。

来源位置应让读者能够直接核验。优先使用可访问的相对链接，并补充章节、消息序号或可定位的原文标记。

可以压缩旧方案的解释，但不能删除方案名称、关键差异和确认状态。

账本中的每个历史版本都必须单独出现，或者由对应行直接链接到完整附录。

不得把多个未确认版本融合成一个新版本后，省略原有版本。

编辑融合可以作为新版本增加，但必须标记为编辑新增且未经确认。

正文只把“已确认”内容写成现行规则。

未确认、他人建议或编辑新增如需进入正文，必须在对应位置直接标明其性质和状态，不能只在文末统一声明。

在缺失位置使用带编号的精确 TODO：

```text
TODO-01：确认失败重试次数。
当前材料同时出现 3 次和 5 次。
```

交付时，在对话中按相同编号集中列出所有 TODO 和冲突。

标明 TODO 是否阻塞当前行动。

- 阻塞：不确认就可能执行错误。
- 非阻塞：可以先行动，在指定阶段前确认即可。

确认后回填文档，并删除对应 TODO。

## 选择结构

按以下顺序确定结构：

1. 用户明确指定的结构。
2. 专项 Skill 或项目规则。
3. 目标目录已有的权威模式。
4. 完成主要阅读任务所需的最小章节。

先判断信息之间是否存在总分、因果、阶段、层次、对象或问题域关系。

存在这些关系时，先提炼能够统领下级信息的宏观主题，再把原始信息点放入对应主题。

不要预设宏观主题数量。单一问题可以只有一个主体，复杂文档也可以有较多主题。

中文内部文档默认用“一、二、三”表达宏观层，用“1、2、3”或项目符号承接主题内部的信息。

操作步骤、检查清单、字段列表和验收项等真正同质且平级的内容，可以保持长列表。

判断是否需要增加上级主题时，询问：

> 这些同级信息是否可以由一个更高层概念准确统领？

可以准确统领时先分组；不能统领时保持平级，不为控制数量强行合并。

默认只使用两层正文标题。

只在子主题需要独立解释、引用或维护时增加第三层标题。

先形成内部骨架，再开始写正文。

## 保持读者连贯

以自己为第一读者，不等于假设读者知道讨论过程和后文章节。

概念可以在概览中被简单提到，但在成为推理前提、比较对象、标题问题、表格分类或图示节点前，必须先解释到足以支撑当前判断。

章节过渡只能使用前文已经建立的概念和结论。

段内相邻句也必须建立清楚的承接、转折、因果、条件、递进、让步或例外关系。不能只保留各句事实，让读者自行补全它们之间的逻辑。

先区分核心主题、前置概念、边界概念、实现细节和生态衍生内容。相关但不属于主线的内容不要直接删除；放在主线之后，并说明为什么现在提到、它是什么、与主线有什么关系。

概念、认知、边界类文档及跨章节重组任务的具体检查方法见 [reader-continuity.md](references/reader-continuity.md)。

## 先判断是否需要修改

原文同时满足以下条件时，默认保持不变：

- 主要阅读任务明确。
- 结构完整且阅读顺序清楚。
- 没有影响理解的重复、歧义或噪声。
- 继续修改不能带来明确收益。

只存在局部问题时，只改对应位置。

局部修正如果暴露出上游概念未定义、章节顺序错误，或者同类问题继续转移到相邻章节，停止逐句修补，重新检查全文的概念依赖和章节衔接。

不要为了展示整理能力而重写短小、清楚的文档。

如果不能指出具体的理解缺陷，就原样保留短小文档。

## 选择表达形式

- 单一事实、定义和结论使用短句。
- 映射、规则和方案对比使用表格。
- 流程、时序、状态和依赖关系使用对应图示。
- 不能进入正文的必要细节使用附录或链接。

在不损害事实、逻辑和语句通顺的前提下，能用一句话说清楚，就不要用两句话。

简洁只能删除重复、无效铺垫，以及不承担事实或逻辑作用的词句。

不得为了缩短篇幅，省略理解所需的前提、转折、因果、条件、递进、让步和例外。

相邻句子的关系可能被误解时，使用准确的连接词明确表达。连接词不是越少越好，也不是越多越好；删掉以后仍能准确理解句间关系，才可以省略。

同一流程存在多个条件或分支，但来源没有说明它们之间的判断顺序、优先级或组合行为时，逐项保留全部条件和分支，并统一明确缺失边界，不得为了语句连贯自行排列。

使用简单、准确的词。

用“读者能否直接知道发生了什么”检查抽象词：

- “管理、控制、治理、处理、能力、机制”等词只起概括作用时，改写为可观察的业务动作。
- 必须保留稳定业务术语时，在第一次出现处写清对象、触发条件、动作和结果。
- 一个概括词覆盖多个动作时，直接列出关键动作，不让读者再查代码或追问含义。

例如，将“会话控制”改为“刷新 Access/Refresh Token、切换个人/企业登录身份、退出指定设备，以及在企业停用或员工离职后清除对应 Token”。

一句话只表达一个主要意思，结束后优先换段。拆分长句后必须保留句间关系，不能把完整推理拆成互不相干的短句。

一个结论只保留一个权威表述。

删除铺垫、软化、辩解和机械总结。

图示能够独立表达时，不再用大段文字复述。

目标环境支持 Mermaid 时，优先直接使用 Mermaid。

不支持 Mermaid 时，先考虑表格，再考虑紧凑 ASCII 图。

## 约束新增与推导

新增图示、表格、示例、代码或 SQL 时，逐项确认其内容能够由来源支持。

不要在图示中补画来源未说明的调用、返回、状态或依赖。

无法由来源直接支持的内容，标记为“推断”“建议”或 TODO。

不要声称一段校验 SQL 或检查步骤证明了它实际没有验证的约束。

合理但非来源事实的执行建议，必须与既有规则明确区分。

## 修改和拆分文档

修改已有文档时，优先局部修改。

只有局部修改不能解决结构问题时，才在原文件内重组全文。

完成去重、简化、图表转换和层级整理后，再判断是否拆分。

不要使用字数、行数或章节数量作为硬性标准。

综合判断：

- 一个阅读任务是否仍要求同时记住过多关联信息。
- 内容是否存在可独立理解、引用或维护的稳定边界。
- 拆分是否降低理解成本，同时保持事实和关系完整。

新文档可以自主拆分，并在形成多份稳定文档时建立目录和索引。

已有文件的移动、重命名、删除或引用调整必须先由用户确认。

已有文档已经足够清楚时，不做无意义修改。

## 保留 AI 自主决策

根据理解成本自主决定：

- 文档类型和主要阅读任务。
- 最小结构、信息顺序、分组和标题层级。
- 表达形式和压缩程度。
- 局部修改、原文件重组或保持不变。
- 新文档的拆分、目录和索引。
- 是否调用可选 Skill。
- 在未命中默认触发条件时，是否执行独立读者测试。

永远不要发明事实或丢弃关键信息。

以下事项必须先由用户确认：

- 在冲突信息中选择结论。
- 作出业务、风险或价值取舍。
- 改变用户指定的结构或项目权威规则。
- 移动、重命名或删除已有文件。
- 执行超出当前任务授权的同步或外部操作。

## 按需编排

普通文档不要调用外部 Skill。

只有当前任务确实需要外部能力时，才读取 [references/orchestration.md](references/orchestration.md)。

准备调用但发现 Skill 不可用时，按 [dependencies.md](references/dependencies.md) 请求一次安装确认；用户拒绝、本轮不能加载或安装失败时执行声明的降级方案。

只调用完成任务所需的最少能力。

外部 Skill 不能决定是否需要图示，也不能覆盖本 Skill 的质量优先级。

## 检查 Markdown 机械完整性

创建或修改本地 Markdown 文件后，先读取 [markdown-check-contract.md](references/markdown-check-contract.md)，再使用当前系统的原生检查器：

- Windows：[check_markdown.ps1](scripts/check_markdown.ps1)
- Linux、macOS：[check_markdown.sh](scripts/check_markdown.sh)

基本调用：

```text
Windows:
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check_markdown.ps1 check --path <file-or-directory>

Linux / macOS:
sh scripts/check_markdown.sh check --path <file-or-directory>
```

`check` 递归检查未闭合代码围栏、不存在的本地链接和重复定义的 `TODO-NN`。

原始材料包含 UUID、数字、代码标识、路径或精确枚举时，再运行：

```text
compare --source <source-file> --output <markdown-file>
```

逐项复核 `source_only` 和 `output_only`，但不要把字面量差异直接判为事实错误。

检查器只负责机械完整性，不能替代来源账本、事实核对、未知管理、去重和理解成本判断。原生检查器不可用时，使用 Agent 文件工具完成同样的只读检查；没有对应工具时说明未执行，不得声称已经通过。

## 验收

每次交付前检查：

1. 关键信息是否完整、准确，未知是否已标记。
2. 定义、边界、动作和验收是否明确。
3. 推理是否成立，相邻句子的承接、转折、因果、条件和例外是否清楚。
4. 语句是否通顺，删掉连接词后是否要求读者自行补全逻辑。
5. 抽象概括词是否已经展开为读者可以直接理解的对象、动作和结果。
6. 是否先形成内容骨架；同级信息是真正平级，还是缺少能够统领它们的上级主题。
7. 标题、过渡句、表格和图示是否只使用前文已经解释的概念。
8. 核心主线和衍生内容是否分开，衍生内容是否有明确入口。
9. 结构和载体是否降低理解成本，同一关系是否在没有新增阅读用途时被正文、列表、表格或图示重复表达。

逐项核对来源账本，特别检查名称、枚举值、数字、顺序、语气和未决版本。

对多轮讨论或多版本材料，再检查一次覆盖闭环：

- 每个结构、分类、数字、时间和关系版本是否都有去向。
- 来源位置、内容性质和采用状态是否能够分别回答。
- 正文语气是否与采用状态一致。
- 编辑融合是否保留了被融合版本，而不是替代后删除。

检查所有新增图示、SQL、代码和建议，确保没有把推导写成事实。

完整冷读一次，只依据最终文档检查跨章节重复、矛盾、缺失前提和前后断裂。

概念或边界类文档、存在跨章节依赖的文档、完成跨章节重组的文档，以及局部修改继续暴露缺失前提的文档，默认执行独立读者测试。

当前环境不能使用独立读者时，按 [reader-continuity.md](references/reader-continuity.md) 完成无讨论上下文的自我冷读。

测试时，只向独立读者提供最终文档和主要阅读任务。

要求独立读者只报告误解、歧义、矛盾、缺失前提及对应位置。

根据结果执行最小修改。

## 交付

直接完成用户要求的文档工作，不额外输出固定模板。

在最终回复中先说明结果，再集中列出仍需确认的 TODO 和冲突。
