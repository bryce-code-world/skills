# 闪电

把内部文档整理成自己能快速理解、AI 能立即行动的形式。

## 遵守质量优先级

按以下顺序处理，后面的目标不能破坏前面的目标：

1. 关键信息完整。
2. 事实准确。
3. 定义与边界无歧义。
4. 容易理解。
5. 表达简洁。
6. 形式美观。

压缩表达，不压缩事实。

## 执行工作流

1. 读取原始材料、目标文件和适用的项目规则。
2. 识别文档类型、主要阅读任务、范围、事实来源和目标环境。
3. 建立内部来源账本，不默认输出这份账本。
4. 判断原文是否已经足够清楚；足够清楚时保持不变。
5. 标记未知、冲突和缺失前提，不自行补全。
6. 选择完成主要阅读任务所需的最小结构。
7. 选择短句、分点、表格、图示、附录或链接。
8. 创建或修改文档，再删除重复、简化语言。
9. 将成稿逐项回对来源账本。
10. 重读全文并完成自检。

主要阅读任务只能有一个：

- 理解。
- 决定。
- 执行。
- 查询、记录或跟踪。

## 保留关键信息

在来源账本中逐项记录：

- 结论、定义、规则、动作和验收。
- 名称、术语、路径、表名、字段名和枚举显示值。
- 数字、单位、时间范围、顺序、条件、例外和失败路径。
- 不同版本、备选方案、观点归属及其确认状态。
- “可能”“建议”“暂定”“已经确认”等语气强度。

材料包含多轮讨论或多个版本时，按语义维度逐项枚举，不抽取“代表版本”代替完整记录。

重点检查：

- 结构和目录的每个版本。
- 分类、清单和步骤的每个版本。
- 数量、范围和时间口径的每个版本。
- 流程、层级、因果和依赖关系的每个版本。
- 同一概念的不同定义及其冲突。

优先保留：

- 结论和定义。
- 前置条件与约束。
- 例外和失败路径。
- 动作与验收标准。

将必要证据、推导、实现细节和历史记录放入附录或独立文档。

删除内容前，确认它是重复表达，不是独立事实。

来源账本中的每一项都必须满足以下一种结果：

- 在正文中准确保留。
- 移入可访问的附录或权威链接。
- 作为未决项或冲突明确标记。

不得静默省略。

不要用近义词替换名称、清单项、步骤名、分类名和约束词。

使用附录或链接承接省略内容时，确保目标文件真实存在且会持续保留。

修改原文件时，不要把“修改前的原文件”当作修改后的权威链接。

如果没有可持续访问的来源文件，就在当前文档中保留完整事实。

成稿前建立“来源项 → 成稿位置或去向”的对应关系。

只有每个来源项都有明确去向，信息核对才算完成。

## 处理未知与冲突

先完成所有确定内容。

区分用户确认、来源事实、他人建议和编辑新增。

不要因为某个方案最后出现，就把它当作已经确认的最终方案。

原文包含多个目录、分类、时间口径、数量或框架版本时，逐项保留差异。

整理对话记录或多轮方案时，增加紧凑的“版本与采用状态”记录。

至少记录：

- 议题。
- 各版本或观点。
- 可核验的来源位置。
- 内容性质。
- 采用状态。

不要把来源、内容性质和采用状态混在同一列。

内容性质至少区分：

- 用户陈述。
- 来源事实。
- 他人建议。
- 编辑新增或推断。

采用状态使用含义明确且前后一致的词，例如：

- 已确认。
- 未确认。
- 暂不采用。
- 冲突待确认。

来源位置应让读者能够直接核验。优先使用可访问的相对链接，并补充章节、消息序号或可定位的原文标记。

可以压缩旧方案的解释，但不能删除方案名称、关键差异和确认状态。

账本中的每个历史版本都必须单独出现，或者由对应行直接链接到完整附录。

不得把多个未确认版本融合成一个新版本后，省略原有版本。

编辑融合可以作为新版本增加，但必须标记为编辑新增且未经确认。

正文只把“已确认”内容写成现行规则。

未确认、他人建议或编辑新增如需进入正文，必须在对应位置直接标明其性质和状态，不能只在文末统一声明。

在缺失位置使用带编号的精确 TODO：

```text
TODO-01：确认失败重试次数。
当前材料同时出现 3 次和 5 次。
```

交付时，在对话中按相同编号集中列出所有 TODO 和冲突。

标明 TODO 是否阻塞当前行动。

- 阻塞：不确认就可能执行错误。
- 非阻塞：可以先行动，在指定阶段前确认即可。

确认后回填文档，并删除对应 TODO。

## 选择结构

按以下顺序确定结构：

1. 用户明确指定的结构。
2. 专项 Skill 或项目规则。
3. 目标目录已有的权威模式。
4. 完成主要阅读任务所需的最小章节。

默认只使用两层正文标题。

将 3～4 个主要信息点视为易于理解的经验值，不作为硬限制。

出现 5 个及以上信息点时，检查是否存在可独立概括的大主题。

按语义分组；不要为控制数量强行合并不同内容。

只在子主题需要独立解释、引用或维护时增加第三层标题。

## 先判断是否需要修改

原文同时满足以下条件时，默认保持不变：

- 主要阅读任务明确。
- 结构完整且阅读顺序清楚。
- 没有影响理解的重复、歧义或噪声。
- 继续修改不能带来明确收益。

只存在局部问题时，只改对应位置。

不要为了展示整理能力而重写短小、清楚的文档。

如果不能指出具体的理解缺陷，就原样保留短小文档。

## 选择表达形式

- 单一事实、定义和结论使用短句。
- 映射、规则和方案对比使用表格。
- 流程、时序、状态和依赖关系使用对应图示。
- 不能进入正文的必要细节使用附录或链接。

能用一句话说清楚，就不要用两句话。

使用简单、准确的词。

一句话只推进一件事，结束后优先换段。

一个结论只保留一个权威表述。

删除铺垫、软化、辩解和机械总结。

图示能够独立表达时，不再用大段文字复述。

目标环境支持 Mermaid 时，优先直接使用 Mermaid。

不支持 Mermaid 时，先考虑表格，再考虑紧凑 ASCII 图。

## 约束新增与推导

新增图示、表格、示例、代码或 SQL 时，逐项确认其内容能够由来源支持。

不要在图示中补画来源未说明的调用、返回、状态或依赖。

无法由来源直接支持的内容，标记为“推断”“建议”或 TODO。

不要声称一段校验 SQL 或检查步骤证明了它实际没有验证的约束。

合理但非来源事实的执行建议，必须与既有规则明确区分。

## 修改和拆分文档

修改已有文档时，优先局部修改。

只有局部修改不能解决结构问题时，才在原文件内重组全文。

完成去重、简化、图表转换和层级整理后，再判断是否拆分。

不要使用字数、行数或章节数量作为硬性标准。

综合判断：

- 一个阅读任务是否仍要求同时记住过多关联信息。
- 内容是否存在可独立理解、引用或维护的稳定边界。
- 拆分是否降低理解成本，同时保持事实和关系完整。

新文档可以自主拆分，并在形成多份稳定文档时建立目录和索引。

已有文件的移动、重命名、删除或引用调整必须先由用户确认。

已有文档已经足够清楚时，不做无意义修改。

## 保留 AI 自主决策

根据理解成本自主决定：

- 文档类型和主要阅读任务。
- 最小结构、信息顺序、分组和标题层级。
- 表达形式和压缩程度。
- 局部修改、原文件重组或保持不变。
- 新文档的拆分、目录和索引。
- 是否调用可选 Skill。
- 是否执行独立读者测试。

永远不要发明事实或丢弃关键信息。

以下事项必须先由用户确认：

- 在冲突信息中选择结论。
- 作出业务、风险或价值取舍。
- 改变用户指定的结构或项目权威规则。
- 移动、重命名或删除已有文件。
- 执行超出当前任务授权的同步或外部操作。

## 按需编排

普通文档不要调用外部 Skill。

只有当前任务确实需要外部能力时，才读取 [references/orchestration.md](references/orchestration.md)。

只调用完成任务所需的最少能力。

外部 Skill 不能决定是否需要图示，也不能覆盖本 Skill 的质量优先级。

## 检查 Markdown 机械完整性

创建或修改本地 Markdown 文件后，先读取 [markdown-check-contract.md](references/markdown-check-contract.md)，再使用当前系统的原生检查器：

- Windows：[check_markdown.ps1](scripts/check_markdown.ps1)
- Linux、macOS：[check_markdown.sh](scripts/check_markdown.sh)

基本调用：

```text
Windows:
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check_markdown.ps1 check --path <file-or-directory>

Linux / macOS:
sh scripts/check_markdown.sh check --path <file-or-directory>
```

`check` 递归检查未闭合代码围栏、不存在的本地链接和重复定义的 `TODO-NN`。

原始材料包含 UUID、数字、代码标识、路径或精确枚举时，再运行：

```text
compare --source <source-file> --output <markdown-file>
```

逐项复核 `source_only` 和 `output_only`，但不要把字面量差异直接判为事实错误。

检查器只负责机械完整性，不能替代来源账本、事实核对、未知管理、去重和理解成本判断。原生检查器不可用时，使用 Agent 文件工具完成同样的只读检查；没有对应工具时说明未执行，不得声称已经通过。

## 验收

每次交付前检查：

1. 关键信息是否完整、准确，未知是否已标记。
2. 定义、边界、动作和验收是否明确。
3. 层级是否必要，同级信息是否清楚，表达是否重复。
4. 结构和载体是否降低了理解成本。

逐项核对来源账本，特别检查名称、枚举值、数字、顺序、语气和未决版本。

对多轮讨论或多版本材料，再检查一次覆盖闭环：

- 每个结构、分类、数字、时间和关系版本是否都有去向。
- 来源位置、内容性质和采用状态是否能够分别回答。
- 正文语气是否与采用状态一致。
- 编辑融合是否保留了被融合版本，而不是替代后删除。

检查所有新增图示、SQL、代码和建议，确保没有把推导写成事实。

完整重读一次，检查跨章节重复、矛盾和前后断裂。

根据误解后果、语义关联程度、结构新颖程度和自身把握，判断是否进行独立读者测试。

测试时，只向独立读者提供最终文档和主要阅读任务。

要求独立读者只报告误解、歧义、矛盾、缺失前提及对应位置。

根据结果执行最小修改。

## 交付

直接完成用户要求的文档工作，不额外输出固定模板。

在最终回复中先说明结果，再集中列出仍需确认的 TODO 和冲突。
