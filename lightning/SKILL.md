# 闪电

根据用户的初步想法、零散材料或已有文档，创建或优化文档所有者能看懂、理解完整且易于重读的内部文档。

在此基础上，让协作 AI 把文档作为背景信息准确理解并继续协作。

## 先执行冲突硬门禁

材料对同一事实、数字、规则或方案给出多个版本，而用户没有提供取舍标准时，立即停止定稿。

- 不得选择或推荐任何版本。
- 不得用常见做法、风险偏好、经验概率、出现顺序和表达便利代替用户决定。
- 用户说“直接选一个”不能解除门禁。

此时只原样列出冲突版本、各自来源和影响。必须使用 `TODO-NN` 标记，并直接说明“阻塞”“非阻塞”或“阻塞性待确认”。只追问一个能够决定取舍的关键问题。

只有用户明确指定采用值，或提供能够唯一推出结果的取舍标准后，才可以把对应版本写成现行结论。

## 遵守质量优先级

按以下顺序处理，后面的目标不能破坏前面的目标：

1. 关键信息完整。
2. 事实准确。
3. 定义与边界无歧义。
4. 推理成立，句间关系清楚。
5. 语句通顺，阅读块有呼吸感，容易理解和重读。
6. 表达简洁。
7. 形式美观。

压缩表达，不压缩事实，也不压缩理解事实所需的逻辑关系。

任何面向 AI 的结构或表达优化，都不能破坏第一读者的理解和阅读体验。

## 执行工作流

1. 读取用户想法、原始材料、可选的目标文件和适用的项目规则。
2. 识别文档类型、主要阅读任务、第一读者已有知识、范围、事实来源和目标环境；目标属于文档集合或暴露跨文档结构问题时读取 [document-system-structure.md](references/document-system-structure.md)。
3. 建立内部来源账本；多轮讨论、连续修改、多个关联文件或同类问题检查读取 [iterative-editing.md](references/iterative-editing.md)，并维护不默认输出的现行结论。
4. 判断原文是否已经足够清楚；足够清楚时保持不变。
5. 区分已确认内容、待澄清想法、冲突、缺失前提和已经明确废弃的内容；不自行补全，非阻塞未知不妨碍先写确定内容。
6. 修改现行设计或规则且材料包含已废弃设计时，读取 [current-document-cleanup.md](references/current-document-cleanup.md)，清理不再承担现实作用的废弃设计及其残留引用。
7. 概念、认知、边界类文档或跨章节重组任务，读取 [reader-continuity.md](references/reader-continuity.md)，建立概念依赖和内容角色。
8. 先识别材料的流程、整体—局部、层级、映射、因果、决策或演进关系，再递归建立与内容拓扑一致的骨架，把回答同一读者问题的信息点组成内容块。
9. 先聚类共同规则、真实差异、例外和未知，再决定是否需要逐对象展开。
10. 选择短句、分点、表格、图示、附录或链接。
11. 创建或修改文档，先检查推理、句间关系、句子负载和视觉分段，再删除重复、简化语言。
12. 将成稿逐项回对来源账本；多轮修改同时核对语义增量和现行结论回归。
13. 只依据最终文档完成冷读和自检。

主要阅读任务只能有一个：

- 理解。
- 决定。
- 执行。
- 查询、记录或跟踪。

## 保留关键信息

在来源账本中逐项记录：

- 结论、定义、规则、动作和验收。
- 名称、术语、路径、表名、字段名和枚举显示值。
- 数字、单位、时间范围、顺序、条件、例外和失败路径。
- 不同版本、备选方案、观点归属及其确认状态。
- “可能”“建议”“暂定”“已经确认”等语气强度。

主要阅读任务是查询、记录或跟踪，或者多个版本仍未确认时，按语义维度逐项枚举，不抽取“代表版本”代替完整记录。

重点检查：

- 结构和目录的每个版本。
- 分类、清单和步骤的每个版本。
- 数量、范围和时间口径的每个版本。
- 流程、层级、因果和依赖关系的每个版本。
- 同一概念的不同定义及其冲突。

优先保留：

- 结论和定义。
- 前置条件与约束。
- 例外和失败路径。
- 动作与验收标准。

将必要证据、推导、实现细节和仍承担现实作用的历史记录放入附录或独立文档。

删除内容前，确认它是重复表达，不是独立事实。

来源账本中的每一项都必须满足以下一种结果：

- 在正文中准确保留。
- 移入可访问的附录或权威链接。
- 作为未决项或冲突明确标记。
- 已确认废弃且不再承担现实作用，从现行文档中删除并由 Git 或任务日志承接历史。

不得静默省略。

不要用近义词替换名称、清单项、步骤名、分类名和约束词。

使用附录或链接承接省略内容时，确保目标文件真实存在且会持续保留。

修改原文件时，不要把“修改前的原文件”当作修改后的权威链接。

如果没有可持续访问的来源文件，就在当前文档中保留完整事实。

成稿前建立“来源项 → 成稿位置或去向”的对应关系。

只有每个来源项都有明确去向，信息核对才算完成。

## 处理未知与冲突

先完成所有确定内容。

区分用户确认、来源事实、他人建议和编辑新增。

不要因为某个方案最后出现，就把它当作已经确认的最终方案。

原文包含多个仍待选择的目录、分类、时间口径、数量或框架版本时，逐项保留差异。

整理对话记录或多轮方案时，增加紧凑的“版本与采用状态”记录。

至少记录：

- 议题。
- 各版本或观点。
- 可核验的来源位置。
- 内容性质。
- 采用状态。

不要把来源、内容性质和采用状态混在同一列。

内容性质至少区分：

- 用户陈述。
- 来源事实。
- 他人建议。
- 编辑新增或推断。

采用状态使用含义明确且前后一致的词，例如：

- 已确认。
- 未确认。
- 暂不采用。
- 冲突待确认。

来源位置应让读者能够直接核验。优先使用可访问的相对链接，并补充章节、消息序号或可定位的原文标记。

历史记录、决策台账或仍承担现实作用的旧方案，可以压缩解释，但不能删除方案名称、关键差异和确认状态。

这些文档中的每个历史版本都必须单独出现，或者由对应行直接链接到完整附录。

不得把多个未确认版本融合成一个新版本后，省略原有版本。

编辑融合可以作为新版本增加，但必须标记为编辑新增且未经确认。

正文只把“已确认”内容写成现行规则。

未确认、他人建议或编辑新增如需进入正文，必须在对应位置直接标明其性质和状态，不能只在文末统一声明。

在缺失位置使用带编号的精确 TODO：

```text
TODO-01：确认失败重试次数。
当前材料同时出现 3 次和 5 次。
```

交付时，在对话中按相同编号集中列出所有 TODO 和冲突。

标明 TODO 是否阻塞当前行动。

- 阻塞：不确认就可能执行错误。
- 非阻塞：可以先行动，在指定阶段前确认即可。
- 阻塞性待确认：来源不足以判断是否可以先行动；不要自行推断阻塞状态。

确认后回填文档，并删除对应 TODO。

## 选择结构

先判断用户表达的是硬结构要求还是载体建议。

- “必须”“只按”“不要改变结构”等要求属于硬结构要求，必须保留指定的列、顺序和层级。
- “能否”“是否可以”“比如用表格”等表达属于载体建议，不限制最终结构。

按以下顺序确定结构：

1. 用户的硬结构要求。
2. 专项 Skill 或项目规则。
3. 目标目录已有的权威模式。
4. 完成主要阅读任务所需的最小章节。

建立骨架时：

- 将读者需要独立理解或记住的一项结论、规则、动作或事实视为信息点。
- 将共同回答同一个读者问题、能够由一个短语准确命名的信息点组成内容块。
- 按文档、章节和小节递归检查总分、因果、阶段、层次、对象、问题域和读者问题关系。
- 同一层的信息点回答不同问题，且各组需要独立定位、理解、引用或维护时，必须分组。
- 内容块需要独立解释、引用或维护时使用小标题；内容较少时使用总述加列表。
- 空行只能分隔段落，不能代替语义分组。
- 操作步骤、检查清单、字段列表和验收项等真正同质且平级的内容可以保持长列表。
- 不预设宏观主题数量；中文宏观层默认用“一、二、三”，内部用“1、2、3”或项目符号。
- 连续步骤、同质清单和不能准确命名的散点保持平级，不机械增加小标题。

判断是否需要增加上级主题时，询问：“这些同级信息是否可以由一个更高层概念准确统领？”

可以准确统领时先分组；不能统领时保持平级，不为控制数量强行合并。

默认只使用两层正文标题；只在子主题需要独立解释、引用或维护时增加第三层标题。

内容较多时，先判断读者是否需要用不同阅读深度恢复结论、依据、状态或行动。

需要时，读取 [progressive-reading.md](references/progressive-reading.md)。先完成全部事实和结论分析，再按阅读任务选择一至三层；这不是固定章节模板。

选择表格前，执行结构压缩决策：

1. 按行为和约束聚类原始信息，不按对象名称机械分组。
2. 先提炼能够覆盖多个对象的共同规则。
3. 分别保留真实差异、例外和未知；未知不能进入共同结论。
4. 共同规则已经覆盖主体时，优先使用“总原则＋例外”，不建立完整逐对象矩阵。
5. 只有对象在多个独立维度上确有差异，且表格支持读者查询或比较时，才使用表格。

不按固定数量或比例判断共同规律。判断依据是行为是否相同、边界是否一致，以及压缩后能否保留全部事实。

验证或修改结构压缩行为时，读取 [structural-compression-cases.md](references/structural-compression-cases.md)。

## 保持读者连贯

以文档所有者为第一读者，不等于假设第一读者仍记得讨论过程或了解后文章节。

概念可以在概览中被简单提到，但在成为推理前提、比较对象、标题问题、表格分类或图示节点前，必须先解释到足以支撑当前判断。

第一次正式解释单个概念时，先用一句白话回答“它是什么”。

再根据当前阅读任务，只补充理解所需的内容：

- 为什么需要它。
- 它怎样起作用。
- 一个能够建立直觉的最小例子。
- 容易误解时必须说明的边界。

已经讲清楚时停止，不机械凑齐固定模板。

章节过渡只能使用前文已经建立的概念和结论。

段内相邻句也必须建立清楚的承接、转折、因果、条件、递进、让步或例外关系。不能只保留各句事实，让读者自行补全它们之间的逻辑。

先区分核心主题、前置概念、边界概念、实现细节和生态衍生内容。相关但不属于主线的内容不要直接删除；放在主线之后，并说明为什么现在提到、它是什么、与主线有什么关系。

概念、认知、边界类文档及跨章节重组任务的具体检查方法见 [reader-continuity.md](references/reader-continuity.md)。

## 先判断是否需要修改

原文同时满足以下条件时，默认保持不变：

- 主要阅读任务明确。
- 结构完整且阅读顺序清楚。
- 没有影响理解的重复、歧义或噪声。
- 继续修改不能带来明确收益。

只存在局部问题时，只改对应位置。

局部修正如果暴露出上游概念未定义、章节顺序错误，或者同类问题继续转移到相邻章节，停止逐句修补，重新检查全文的概念依赖和章节衔接。

不要为了展示整理能力而重写短小、清楚的文档。

如果不能指出具体的理解缺陷，就原样保留短小文档。

## 选择表达形式

- 单一事实、定义和结论使用短句。
- 多对象在多个独立维度上的映射、查询和方案对比使用表格。
- 流程、时序、状态和依赖关系使用对应图示。
- 不能进入正文的必要细节使用附录或链接。

一个规则单元只回答一个可独立检查的问题。规则单元通常由对象、条件、动作和结果组成。

一个短句能够完整承载一个规则单元时保持一句，不要为了减少句数而把第二个条件、例外、排序、联动动作或终止条件塞进同一句。

一个规则单元包含多项平级条件、步骤或结果时，先写总述，再用列表承接。

简洁只能删除重复、无效铺垫，以及不承担事实或逻辑作用的词句。

不得为了缩短篇幅，省略理解所需的前提、转折、因果、条件、递进、让步和例外。

相邻句子的关系可能被误解时，使用准确的连接词明确表达。连接词不是越少越好，也不是越多越好；删掉以后仍能准确理解句间关系，才可以省略。

同一流程存在多个条件或分支时，逐项保留全部条件和分支。

来源没有说明判断顺序、优先级或组合行为时，统一明确缺失边界，不得为了语句连贯自行排列。

使用简单、准确的词，并用“读者能否直接知道发生了什么”检查抽象词：

- “管理、控制、治理、处理、能力、机制”等词只起概括作用时，改写为可观察的业务动作。
- 必须保留稳定业务术语时，在第一次出现处写清对象、触发条件、动作和结果。
- 一个概括词覆盖多个动作时，直接列出关键动作，不让读者再查代码或追问含义。

例如，将“会话控制”改为“刷新 Access/Refresh Token、切换个人/企业登录身份、退出指定设备，以及在企业停用或员工离职后清除对应 Token”。

完成内容块分组后，再分别判断逻辑完整性和视觉阅读块。

相邻完整句分别承载不同结论、规则、动作、边界或引用时，默认在中间空一行，成为两个 Markdown 段落。

只有拆分会造成主语、指代、条件或逻辑含义不完整、歧义或原意改变时，才保留同段。同一主题、同一对象或时间连续本身都不是合段理由。

不要机械拆分分号、列表、表格单元格或不能独立成立的上下句，也不要用固定字数、句数或标点数量决定换段。

将以下情况标记为句子负载复核候选，但不要自动判错：

- 正文句子不少于 55 个可见字符。
- 正文句子包含至少 3 个逗号、分号或冒号。
- 正文句子同时承载多个条件、动作、例外、排序或联动结果。

字符数和标点数只用于发现候选，不是写作目标。YAML frontmatter、标题、表格行、代码围栏和 Markdown 链接目标不参与机械统计。

`readability` 不检查表格行，因此必须人工检查每个表格单元是否混入多个规则单元。

一个结论只保留一个权威表述。

删除铺垫、软化、辩解和机械总结。

图示能够独立表达且目标环境支持 Mermaid 时，直接使用 Mermaid，不再用大段文字复述。

生成 Mermaid 图时，按 [结构](references/diagram-role-node-layering.md) → [阶段](references/diagram-stage-coverage.md) → [闭环](references/diagram-flow-closure.md) → [落地对象](references/diagram-key-objects.md) 检查图示、路径和实现信息。

不支持 Mermaid 时，先考虑表格，再考虑紧凑 ASCII 图。

## 约束新增与推导

新增图示、表格、示例、代码或 SQL 时，逐项确认其内容能够由来源支持。

不要在图示中补画来源未说明的调用、返回、状态或依赖。

无法由来源直接支持的内容，标记为“推断”“建议”或 TODO。

不要声称一段校验 SQL 或检查步骤证明了它实际没有验证的约束。

合理但非来源事实的执行建议，必须与既有规则明确区分。

## 修改和拆分文档

修改已有文档时，优先局部修改。

只有局部修改不能解决结构问题时，才在原文件内重组全文。

局部修改给原句增加第二个条件、例外、排序或联动结果时，重新检查该规则所在段落，不把新增事实直接接到原句末尾。

完成去重、简化、图表转换和层级整理后，再判断是否拆分。

不要使用字数、行数或章节数量作为硬性标准。

综合判断：

- 一个阅读任务是否仍要求同时记住过多关联信息。
- 内容是否存在可独立理解、引用或维护的稳定边界。
- 拆分是否降低理解成本，同时保持事实和关系完整。

新文档可以自主拆分，并在形成多份稳定文档时建立目录和索引。

已有文件的移动、重命名、删除或引用调整必须先由用户确认。已有文档已经足够清楚时，不做无意义修改。

## 保留 AI 自主决策

根据理解成本自主决定：

- 文档类型和主要阅读任务。
- 最小结构、信息顺序、分组和标题层级。
- 表达形式和压缩程度。
- 局部修改、原文件重组或保持不变。
- 新文档的拆分、目录和索引。
- 是否调用可选 Skill。
- 在未命中默认触发条件时，是否执行独立读者测试。

永远不要发明事实或丢弃关键信息。

以下事项必须先由用户确认：

- 在冲突信息中选择结论。
- 作出业务、风险或价值取舍。
- 改变用户的硬结构要求或项目权威规则。
- 移动、重命名或删除已有文件。
- 执行超出当前任务授权的同步或外部操作。

## 按需编排

普通文档不要调用外部 Skill。

只有当前任务确实需要外部能力时，才读取 [references/orchestration.md](references/orchestration.md)。

只使用当前环境已经可用且用户允许的外部能力。外部 Skill 不可用时，执行 [references/orchestration.md](references/orchestration.md) 中的降级方案。

本 Skill 不安装或更新其他 Skill、插件或运行时。

只调用完成任务所需的最少能力。

外部 Skill 不能决定是否需要图示，也不能覆盖本 Skill 的质量优先级。

## 检查 Markdown 机械完整性

创建或修改本地 Markdown 文件后，先读取 [markdown-check-contract.md](references/markdown-check-contract.md)，再使用当前系统的原生检查器：

- Windows：[check_markdown.ps1](scripts/check_markdown.ps1)
- Linux、macOS：[check_markdown.sh](scripts/check_markdown.sh)

基本调用：

```text
Windows:
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check_markdown.ps1 check --path <file-or-directory>

Linux / macOS:
sh scripts/check_markdown.sh check --path <file-or-directory>
```

`check` 递归检查未闭合代码围栏、不存在的本地链接和重复定义的 `TODO-NN`。

随后运行句子负载筛选：

```text
Windows:
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check_markdown.ps1 readability --path <file-or-directory>

Linux / macOS:
sh scripts/check_markdown.sh readability --path <file-or-directory>
```

`readability` 输出两类非阻断候选：`warnings` 保存高负载正文句，`paragraph_reviews` 保存包含两个及以上完整句的普通正文段落。任一候选存在时，`review_required` 为 `true`；成功扫描仍使用退出码 `0`。

逐项人工判断候选。只有拆分会造成主语、指代、条件或逻辑含义不完整、歧义或原意改变时，段落候选才保留同段。

原始材料包含 UUID、数字、代码标识、路径或精确枚举时，再运行：

```text
compare --source <source-file> --output <markdown-file>
```

逐项复核 `source_only` 和 `output_only`，但不要把字面量差异直接判为事实错误。

检查器只负责机械完整性，不能替代来源账本、事实核对、未知管理、去重和理解成本判断。原生检查器不可用时，使用 Agent 文件工具完成同样的只读检查；没有对应工具时说明未执行，不得声称已经通过。

## 验收

每次交付前检查：

1. 用户想法、零散材料或原文中的关键信息是否完整、准确，未知是否已标记。
2. 定义、边界、动作和验收是否明确。
3. 推理是否成立，相邻句子的承接、转折、因果、条件和例外是否清楚。
4. 语句是否通顺，删掉连接词后是否要求读者自行补全逻辑。
5. 每句话是否只承载一个规则单元，读者是否需要回读才能复述条件、动作和结果。
6. 抽象概括词是否已经展开为读者可以直接理解的对象、动作和结果。
7. 单个概念是否先用一句白话说明“它是什么”，再只补充当前理解所需的原因、作用方式、例子和边界。
8. 多完整句普通段落是否已逐项复核；只有拆分会造成主语、指代、条件或逻辑含义不完整、歧义或原意改变时才保留同段。
9. 是否递归检查文档、章节和小节；不同读者问题是否已组成内容块；空行是否被误当成语义分组。
10. 标题、过渡句、表格和图示是否只使用前文已经解释的概念。
11. 核心主线和衍生内容是否分开，衍生内容是否有明确入口。
12. 结构是否反映内容拓扑；每个阅读层和载体是否有独立用途，同一关系是否被正文、列表、表格、图示或相邻文档无效重复。
13. 文档集合是否职责明确且同一结论只有一个权威位置；只读开头能否恢复核心信息，后续支撑与完整展开是否各有用途。
14. 读者能否一次复述核心结论和例外，未知是否仍保持独立状态。
15. 是否先满足文档所有者的理解和阅读；AI 能否把文档作为背景信息准确理解，且相关优化没有破坏第一读者体验。
16. 现行设计是否仍在解释已经废弃且无现实作用的方案，相关入口、流程、字段、职责、示例、验收和引用是否一并清理。
17. 时序图角色和流程图节点是否必要、无重复且没有缺少闭环责任；过载时是否按语义边界建立总览图和细节图。
18. Mermaid 图是否通过阶段、闭环与落地对象检查，且所有准确名称都有来源或标记待设计。

逐项核对来源账本，特别检查名称、枚举值、数字、顺序、语气和未决版本；多轮或同类修改再核对现行结论、语义增量、正确反例和目标范围外变化。

对历史记录、决策台账或仍有未决版本的材料，再检查一次覆盖闭环：

- 每个结构、分类、数字、时间和关系版本是否都有去向。
- 来源位置、内容性质和采用状态是否能够分别回答。
- 正文语气是否与采用状态一致。
- 编辑融合是否保留了被融合版本，而不是替代后删除。

检查所有新增图示、SQL、代码和建议，确保没有把推导写成事实。

完整冷读一次，只依据最终文档检查重复、矛盾、缺失前提、前后断裂和节内散点，并复述核心结论、例外和未知。

概念或边界类文档、存在跨章节依赖的文档、完成跨章节重组的文档，以及局部修改继续暴露缺失前提的文档，默认执行独立读者测试。

当前环境不能使用独立读者时，按 [reader-continuity.md](references/reader-continuity.md) 完成无讨论上下文的自我冷读。

测试时，只向独立读者提供最终文档和主要阅读任务。

要求独立读者只报告误解、歧义、矛盾、缺失前提、需要回读或无法一次复述的句子及对应位置。

根据结果执行最小修改。
