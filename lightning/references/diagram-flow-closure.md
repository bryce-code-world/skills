# Mermaid 流程闭环

流程闭环是指：在图示声明的范围内，每个触发和条件分支最终都到达明确的业务结果、终止状态或范围交接。

闭环不等于给所有异步消息补画回执，也不等于把来源没有说明的后续行为补齐。

## 闭环规则

- 写明流程由谁、由什么事件或条件触发。
- 同步请求必须返回成功、失败或明确的受理状态，不能停在后端内部处理节点。
- 每个条件分支必须重新汇合，或者到达独立的结果、终止状态或范围交接。
- 循环和重试必须写明退出条件，以及成功、失败或停止后的去向。
- 外发事件、IM 或 WebSocket 消息不能只停在消息系统或中间服务。
- 来源明确实际接收方时，继续画到实际接收方。
- 来源明确接收方收到消息后的动作时，继续画出该动作。例如：`业务 IM → 受影响相关用户的设备前端 → 重新获取权限`。
- 异步单向通知不要求补画确认回执。后续行为超出当前范围时，标明实际接收方和“后续处理不在本图范围”。

## 来源边界

只画来源能够支持的触发者、处理者、接收者、动作和结果。

来源没有说明实际接收方或后续动作时，不得自行补画。

根据缺失性质，标记范围交接、未知或 TODO：

- 消息确认或业务回执。
- 离线投递和失败重试。
- 多设备同步策略。
- 接收方未被来源说明的刷新、跳转或再次请求。

“看起来完整”不能替代事实准确。

## 交付前验证

仅依据最终图示逐条追踪：

1. 每个入口是否都能回答“谁或什么触发”。
2. 每条成功路径和失败路径是否都到达结果、终止状态或明确交接。
3. 每个分支是否都有去向，每个循环是否都有退出条件。
4. 每条外发消息是否写明实际接收方；来源不足时，是否明确标记未知和范围交接。
5. 来源支持时，是否写明接收方下一步动作。
6. 是否存在停在中间件、内部服务或无后续箭头的悬空业务节点。
7. 为形成闭环而新增的节点、返回、回执和动作是否都有来源依据。

以上任一项不能确认时，不得声称流程已经闭环。
