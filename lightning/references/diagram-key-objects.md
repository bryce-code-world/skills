# Mermaid 关键落地对象

当流程图或时序图用于开发、联调、审查、排障或实施时，检查关键落地对象。

关键落地对象是读者定位当前步骤、实现接口和状态载体所需的准确名称，不是固定技术清单。

仅用于业务理解的图，不强制增加来源没有提供的技术细节。

## 按作用选择对象

关键性不由对象所属的技术类型决定。

判断标准是：遗漏后，读者能否定位入口、契约、处理位置、状态载体、路由方式、接收方和结果。

只加入当前链路实际涉及、且会影响理解或实施的对象：

- 触发与入口：用户动作、HTTP 方法与路由、RPC 入口、Webhook、定时任务、消息消费者或命令入口。
- 接口与契约：接口或 Proto 方法、请求与响应类型、Schema 或协议版本。事件链路还包括事件类型、业务类型和消息 `title`。
- 调用与处理：调用方、被调用服务、组件、任务、处理器和准确方法。
- 状态载体：实际读写的表、缓存 Key、索引、文件、对象存储路径、配置项或其他持久化对象。
- 异步路由：消息队列的 topic、exchange、queue、routing key、订阅、消费者或消费者组。

  当前链路实际使用重试或死信机制时，还包括对应入口。
- 投递与接收：WebSocket、IM、推送、邮件或其他通道，以及实际接收的系统、用户和设备范围。
- 结果与后续动作：返回结果、状态变化，以及接收方随后调用的接口或执行的动作。

以上是对象角色示例，不是封闭枚举。

其他技术对象只要承担同等定位作用，也按相同规则判断。

事件存在外层事件类型和内层业务类型时，分别写明，不能合并成“发送消息”。

某类对象没有参与当前链路时，不为凑齐清单而增加。

字段全集、完整表清单、SQL、内部函数和协议细节不影响当前链路理解时，放在图下说明、表格或权威链接中。

## 名称与来源

入口、接口、方法、状态载体、消息标识、路由对象和接收动作必须来自用户材料、代码、协议、配置或其他权威来源。

来源只确认职责但没有给出名称时，标记“待设计”或带编号 TODO。

不得根据命名习惯自行创造准确名称。

这包括方法、事件枚举、消息 `title`、topic、routing key、缓存 Key、表名和前端接口。

来源存在多个冲突名称时，保留冲突并执行 Lightning 的冲突硬门禁。

## 控制信息密度

一张图只承担一个主要阅读任务和一条可连续追踪的主链路。

出现以下情况时，优先拆成能够独立阅读的图：

- 主链路与条件触发的附加链路交叉。
- 不同接收方、触发条件或后续动作导致连线反复跨越。
- 为放入落地对象而需要在多个位置重复同一组标签。
- 读者无法从入口连续追踪到结果，需要来回跳读。

拆图用于分离阅读任务，不等于增加业务阶段。

同一条主链仍然清楚时，保留一张图，把完整对象清单和补充规则下沉到图后。

## 交付前验证

1. 先确定图的主要阅读任务、入口、结果和范围。
2. 从来源提取本链路实际涉及的入口、契约、处理位置、状态载体、路由对象、接收方和结果。
3. 逐项确认对象已经进入对应节点或消息，或者有明确的图下权威入口。
4. 检查每个准确名称都有来源，未知名称已经标记“待设计”或 TODO。
5. 检查以下概念没有被混写：
   - 事件类型与业务类型；
   - topic 与消息 `title`；
   - queue 与 routing key；
   - 缓存 Key 与批量匹配模式。
6. 仅依据最终图示连续追踪主链；需要反复跳线时，重新拆分主链与附加链路。
7. 确认没有为凑齐技术清单加入当前链路未使用的对象。

关键对象缺失会使图无法指导实施。

对象堆叠破坏主线时，图同样不合格。
