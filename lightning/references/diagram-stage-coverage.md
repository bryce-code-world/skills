# 多阶段 Mermaid 图

生成流程图或时序图时，先判断是否存在多个业务阶段，再决定是否增加阶段示意。

## 判断是否存在阶段

阶段是一段具有独立业务目标和可识别起止边界的流程，不是对技术处理步骤的分组。

出现以下任一情况时，可以形成新的业务阶段：

- 用户或另一个业务参与者需要发起下一次独立操作或作出新的决定。
- 流程暂停、等待，并在之后由新的触发条件恢复。
- 前一个业务结果已经完成，后续流程以新的业务目标、触发条件或可观察状态继续。
- 用户或权威来源已经明确给出能够覆盖相关流程的业务阶段。

用户只要求“增加阶段示意”但没有给出阶段边界时，仍按以上业务边界判断，不按节点机械分组。

以下情况本身不能作为拆分阶段的依据：

- 同一次用户或前端操作触发的请求，以及该请求内的鉴权、校验、查询、事务、缓存、消息和通知。
- 后端服务、组件、技术层或调用对象发生变化。
- 图中节点较多、链路较长，或者存在条件分支、失败处理和重试。

同一次完整操作从发起到返回业务结果，默认属于一个阶段。

后端内部处理保持原有顺序，但不单独形成业务阶段。

来源没有明确阶段，且不能从业务操作或状态边界判断出多个阶段时，保持连续流程，不增加“阶段一”或阶段容器。

## 阶段表达

- 只有流程存在两个以上业务阶段时，才增加阶段示意。
- 在图内标出每个阶段的名称和简短说明。
- 阶段容器沿流程推进方向，从本阶段第一项覆盖到最后一项。
- 容器纳入本阶段的全部节点、消息、条件分支和循环。
- 不得只标出阶段起点，不得漏包本阶段流程，也不得把下一阶段流程包入当前阶段。

## Mermaid 实现

- 普通流程图优先使用 `subgraph` 包住阶段内的节点。
- 时序图优先使用阶段区域包住阶段内的消息。
- 时序图的阶段说明需要横向展开时，其范围覆盖本阶段涉及的参与者。
- 具体语法可以根据目标 Mermaid 版本调整，但阶段边界和覆盖关系不能丢失。

交付前仅依据图示检查：

- 每个阶段边界是否都能用业务操作、业务目标或状态变化解释。
- 单次完整操作是否没有被后端技术步骤强拆。
- 存在多个业务阶段时，读者能否识别阶段数量、名称、作用、边界和切换点。
- 每个步骤、分支与循环是否只属于正确阶段。
