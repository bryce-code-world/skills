# 架构图

先把架构事实编译成明确的绘图规格，再复用合适的底层能力，生成一个可信、清晰、可直接打开的 HTML 文件。

## 维护依赖与版本

每次触发时读取 [dependencies.md](references/dependencies.md)，按其规则检查本 Skill 版本，并只为当前实际场景准备依赖。

本地版本以 [release.json](references/release.json) 为准。

已声明的白名单依赖缺失时自动安装，不询问用户。未知来源、来源变化、版本无法核验、安装校验失败或同名目标无法隔离时停止对应步骤并降级；自动安装不扩大为自动更新、覆盖脏源码、上传或发布授权。

## 建立架构事实

1. 读取用户材料、参考图、目标文件和适用的项目规则。
2. 读取 [architecture-brief.md](references/architecture-brief.md)，建立内部架构图规格。
3. 区分当前架构、目标架构、规划和未知，不把它们融合为一个确定状态。
4. 让每个节点、分组、边界和有向关系都能回到用户说明、文档或代码证据。
5. 输入零散但能够整理时使用 `lightning`；关键职责、方向或边界仍冲突时，先完成确定部分，停止绘制对应关系。

参考图只决定视觉方向和结构启发，不能成为架构事实来源。

## 选择主绘图路径

读取 [routing.md](references/routing.md)，一次任务只选择一个主路径：

- 静态企业蓝图、分层架构和技术栈总览：读取隔离的 `markdown-viewer/architecture` 规则源，只选当前需要的布局、样式和连接器规则。
- 架构演化、逐层探索或路径聚焦：只有交互明显降低理解成本时使用 `visual-cognitive-learning`。
- 已确认结构需要品牌化或视觉定向：使用 `frontend-design` 辅助视觉方案，但不允许它改变架构事实。

静态图已经足够时，不增加交互。简单三层架构不套用复杂企业蓝图。

## 生成企业蓝图

写 HTML 前读取 [enterprise-blueprint.md](references/enterprise-blueprint.md)。

1. 先确定阅读任务、主结构和视觉重点，再确定画布尺寸。
2. 先布局容器与节点，再绘制连接关系。
3. 使用内联 SVG 或等价离线图标；不使用 Emoji 充当正式主图标。
4. 主路径优先使用直角线；不得让连线、箭头或标签穿过组件文字。
5. 内容过密时聚合、下沉说明、扩大画布或拆分视图，不持续缩小文字。
6. 横切能力使用贯穿侧栏或明确边界表达，不在每层重复复制。

## 守住单文件契约

最终产物必须：

- 只有一个 `.html` 文件，并通过 `file://` 直接打开。
- 内嵌 CSS、JavaScript、SVG、数据和当前实际使用的图标。
- 不依赖服务器、构建步骤、外部脚本、样式表、字体、图片、iframe 或网络接口。
- 不包含密钥、Token、Cookie、绝对来源路径或与主图无关的原始材料。
- JavaScript 失败时仍保留可理解的静态主体。
- 没有必要交互时不添加伪按钮、装饰动画或隐藏信息。

## 验证与交付

生成后读取 [validation.md](references/validation.md)，依次完成事实、HTML、浏览器和视觉四层验收。

必须实际打开并截图检查目标桌面尺寸和一个较窄视口；浏览器不可用时明确标记浏览器与视觉验收未完成，不声称最终通过。

普通任务只交付最终 HTML。内部架构图规格、截图和检查记录属于过程证据，不默认进入交付包。交付时简要说明主结构、实际执行的验证和仍未绘制的未知关系。

## 行为验收

发布后在全新会话中使用 [behavior-cases.md](references/behavior-cases.md) 验证触发、非触发、权限边界和失败处理。案例只定义预期，不授权扫描、写入或发布。
