# 架构图规格

在写 HTML 前建立内部规格。普通任务不默认交付这份规格。

## 一、事实门禁

输入至少包含一种可靠材料：

- 已确认的架构说明或设计文档。
- 用户明确列出的组件、分组、关系和边界。
- 可以由当前代码、配置或接口证据验证的架构事实。
- 参考图与需要替换的真实架构内容。

先区分：

- 当前事实。
- 目标或规划。
- 用户判断。
- 编辑推断。
- 未知与冲突。

不要把最后出现的方案当成已经确认，也不要根据组件常见用法补造调用方向。

## 二、规格字段

| 字段 | 必须回答的问题 |
|---|---|
| 阅读任务 | 读者看完要理解或决定什么？ |
| 受众 | 面向管理者、产品、架构师、开发还是客户？ |
| 时间状态 | 当前、目标、规划还是演进对比？ |
| 主结构 | 分层、分域、中心—外围、流程还是混合结构？ |
| 节点 | 哪些组件必须出现，正式名称和一句职责是什么？ |
| 分组 | 哪些节点属于同一层、域、平面或边界？ |
| 关系 | 哪些连接已确认，方向、类型和标签是什么？ |
| 横切能力 | 安全、治理、监控、租户等如何跨层表达？ |
| 外部依赖 | 哪些系统不属于架构本体？ |
| 视觉重点 | 第一眼必须看见哪一层、路径或能力？ |
| 密度预算 | 哪些进入主图，哪些下沉为说明或图例？ |
| 交互必要性 | 操作与可观察反馈是什么？ |

## 三、关系账本

为每条需要绘制的关系记录：

| 项 | 内容 |
|---|---|
| 来源节点 | 正式节点标识 |
| 目标节点 | 正式节点标识 |
| 方向 | 单向、双向或无方向 |
| 类型 | 同步调用、异步事件、数据流、控制或治理 |
| 标签 | 只有帮助理解时才写 |
| 依据 | 用户说明、文档位置或代码证据 |
| 状态 | 已确认、待确认、规划或推断 |

正文只把已确认关系画成确定连线。待确认、规划和推断必须直接可辨认，或不进入主图。

## 四、密度门禁

出现以下情况时先压缩规格，不直接缩小字号：

- 同一节点承担多个不相干职责。
- 同一层包含大量等权节点，读者无法识别重点。
- 次要关系数量超过主路径。
- 标题、说明、图例和组件正文重复表达同一结论。
- 一张图同时承担现状、目标、演进和实施计划。

优先聚合等价节点、下沉长说明、拆分时间状态或保留一条主路径。
