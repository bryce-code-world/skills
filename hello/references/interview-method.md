# 访谈方法

## 一、访谈协议与模型镜头

首次建档先确认：

- 建档目的和期望 AI 理解的重点。
- 用户指定的资料根目录。
- 可以读取的旧资料范围。
- 不愿讨论、不得记录或只允许记录影响摘要的主题。
- 原始记录默认采用结构化问答。
- 用户可以随时暂停、跳过、修正、撤回或删除。
- 确认每轮原始记录采用结构化问答、影响摘要或不落盘；高敏感选择可以逐轮改变。

访谈用于建立长期协作背景，不是治疗、诊断或人格测评。

访谈不从零发明“完整的人”分类。提问时按需要切换几个互补镜头：人生叙事镜头关注章节、转折和意义；功能与环境镜头关注身体、精力、活动和现实约束；价值镜头关注取舍和冲突；行为镜头关注跨事件的可观察模式；决策镜头关注约束、权衡、选择和结果。镜头是探索工具，不是用户必须接受的标签或量表结果。

## 二、提问原则

- 一次只问一个核心问题。
- 先问开放问题，再澄清时间、人物、条件和结果。
- 让用户用自己的语言定义重要内容。
- 不在问题中预埋性格结论或价值判断。
- 对模糊概括追问具体事件，对具体事件追问其意义。
- 区分“当时怎么想”和“现在怎么看”。
- 不把“不知道”、沉默或跳过解释为隐藏事实。
- 发现矛盾时并列两个版本，请用户澄清；不能自行融合。
- 用户没有表示“不知道”或要求比较时，先保持开放提问，不用二选一或多选一替代用户定义问题。
- 选项、分类和顺序如果由 AI 提供，必须明确标注为探索框架，不记录为用户原始观点。

## 三、正式访谈入口：先消化收件箱

首次建档、继续访谈、增量回访和集中审核都先执行同一闸门：

前置检查（强制）：在读取任何个人资料或运行会读取资料的命令前，先判断产出物去向；若产出物会离开本地，先读取并执行 [context-contract.md](context-contract.md)，列出最小范围、抽象化方式和敏感排除，协议完成前不得读取整篇档案或整套 `权威/`。本地任务可在授权范围内先运行 `status`。

1. 运行只读 `status`，读取实际 `capture_mode`、`capture_strategy`、兼容字段 `last_capture_disclosed_at`（上次受控知情审计时间）、进度版本、维护阶段和候选数量。
2. 向用户披露当前采集策略和上次知情审计时间；用户确认理解后调用 `record-disclosure --capture-mode <当前模式> --confirmed --root <已授权目录>`。时间戳为空、过期或用户不记得时，先询问是否沿用；不确定则暂停暂存并改回 `prompt` 或 `explicit`。
3. 列出未处理候选，逐条让用户接受、修正、合并、追问、推迟或拒绝。未处理候选不是事实，也不能因为摘要看起来合理就自动归档。
4. 对已接受或修正的候选，建立对应的声明、事件或决策差异；目标 P1 协议完成后，用户确认再通过受控 `apply` 更新权威层、覆盖矩阵、候选状态和日志。当前 schema 2 只对根级旧档案执行 `diff`/`apply`，不能把实体拆分写入当作已完成能力。
5. 候选审核完成或用户明确跳过后，目标包使用机器 `resume_cursor`；兼容 schema 2 以《访谈进度》中的 `next_question`/恢复游标文本为准。不要声称当前 `status` 已返回机器可执行游标。跳过的候选保留待处理状态，并在下次入口再次提示。

这一步是“先消化新信息、再从进度继续”的固定协议，不是可选的礼貌提示。

### 布局分支护栏

先判定资料空间是兼容 schema 2 还是目标包，再选择写入方式。现有三套适配器的 `record-turn`、`diff` 和 `apply` 只适用于兼容 schema 2 根目录；目标包分支禁止调用现有 `record-turn`，当前只能生成待确认的目标实体/聚合索引草稿并保留宿主游标，待目标 P1 协议冻结并实现、再经 P3 迁移切换后才可物理写入。

## 四、基础主题地图

按用户情况调整顺序和深度，不机械完成清单：

1. 身份、角色、语言、使用目的与当前处境。
2. 人生章节与关键转折。
3. 成长环境与家庭影响。
4. 教育、自学和知识结构。
5. 职业、项目、选择和成果证据。
6. 能力、经验和可迁移优势。
7. 健康、精力、压力和恢复边界。
8. 经济结构、安全感和风险承受能力。
9. 关系、支持网络和现实责任。
10. 习惯、行动、决策和复盘方式。
11. 情绪模式与压力应对。
12. 认知、信息来源和世界观。
13. 价值观、意义和不可接受的边界。
14. 高光、低谷、失败、遗憾和损失。
15. 时间、金钱、关系、渠道和环境资源。
16. 未来愿景、目标、担忧和待验证方向。
17. 希望 AI 如何提问、提醒、质疑和使用信息。

### 主题问题层级与恢复游标

为避免只得到零散故事，每个主题按四个可重复的层级推进；层级是提问导航，不是必须填满的表格：

1. `orientation`：先让用户用自己的话说明主题当前是什么、为什么重要或暂不讨论。
2. `evidence`：追问一个具体事件、选择、结果、材料或可观察例外，建立来源锚点。
3. `reflection`：区分当时理解、现在理解、形成的能力/偏好/约束和适用边界。
4. `change`：确认何时可能失效、最近是否变化、下次复核看什么信号。

问题使用稳定的 `question_id=<topic_id>.<layer>.<sequence>`（例如 `capability.evidence.01`，示例 ID 不代表真实资料）。`访谈进度` 的 `resume_cursor` 只保存下一个问题 ID 和会话/轮次版本，不复制回答；用户跳过某层时记录 `deferred` 或 `unknown`，不能把未问过当作 `confirmed_minimum`。每个主题的最低覆盖锚点见 [profile-architecture.md](profile-architecture.md) 和目标模板的 `主题覆盖矩阵.md`，P1 冻结时再锁定字段与证据等级。

## 五、人生骨架

先请用户把人生想成一本书，给主要章节命名并说明大致时间、主题和转折原因。建议 2 至 7 个章节，但不强制数量。

建立骨架后，再从用户认为最重要的章节进入具体场景。优先了解：

- 高点。
- 低点。
- 转折点。
- 重要选择。
- 失败或遗憾。
- 健康、关系或经济挑战。
- 对未来影响最大的经历。

每个场景尽量获得：发生时间、地点、相关人物、现实条件、用户选择、结果、当时感受、现在理解和长期影响。

当回答中出现可复用的经历时，优先整理为 `Event`；当回答解释“为什么这样选”时，补充 `Decision`。事件至少保留背景、选择、结果、当时理解、现在理解和影响；决策至少保留问题、选项、约束、权衡、选择、结果和复盘。两者都要回指原始来源，不把 AI 的概括写成用户原话。

## 六、阶段确认

每个主题结束后，只输出四类内容：

- 已确认：用户明确确认的事实陈述。
- 本人理解：用户对自己和经历的解释。
- 未知冲突：缺失、模糊或相互矛盾的信息。
- AI 假设：有一定证据但尚未由用户确认的模式。

先让用户修正，再写入权威档案。AI 假设即使合理，也不能因用户没有反对而自动升级。

## 七、每轮持久化

收到一轮回答后按固定顺序处理：

1. 完成必要的单个澄清，不把多个主题塞进一轮。
2. 生成本轮不可变记录，使用稳定的 `session-id` 和递增或稳定的 `turn-id`。
3. 生成完整但精简的《访谈进度》候选，只保留恢复访谈需要的信息。
4. 正式 target 使用 `record-turn` 和当前 `progress_version` 原子写入不可变轮次、目标游标和相关事务元数据；实体状态与聚合索引仍必须由目标事务更新，不能把草稿当作已确认事实。
5. 目标写入成功后再提出下一问题；失败时先恢复或说明未落盘，不把“已回答”误报成“已保存”。

同一轮因重试再次执行时沿用相同的会话和轮次编号，以获得幂等结果。原始记录不得整会话反复覆盖，也不得绕过适配器直接追加。

## 八、覆盖、完成与暂停

每个主题都要在 `主题覆盖矩阵.md` 中标记覆盖状态：`not_started`、`signals_only`、`partial`、`confirmed_minimum`、`deepened`、`stale`、`conflicted`、`declined` 或 `not_applicable`，同时标注它是“基线必答”还是“可长期补充”。若 `status.baseline_split_unknown=true`，先完成分组确认或迁移，不能以空清单收口。用户明确拒答或不适用时，记录原因范围但不追问，也不让该主题继续阻塞基线收口。

基线完成标准：

- 核心主题已有基本信息或明确标为暂不收集。
- 主要人生阶段能够串联。
- 当前资源、约束、责任和目标已经确认。
- 重要结论可以追溯到访谈或资料。
- 未知和冲突仍然清晰可见。

用户疲惫、不适或要求暂停时，先用当前轮次协议记录已确认进度和下一问题，再结束。连续同一主题约 6—8 轮时先做阶段检查点；如果出现重复、疲惫或内容转为具体项目方案，应暂停并询问继续、转任务文档或暂不收集。长访谈中定期用一句话询问精力或是否继续。

达到基线完成标准不等于自动切换阶段。先展示完成判断并取得确认，再显式设置 `first-review` 和一个月后的回访时间。

正式 `session_id` 跨自然日、跨设备、超过 50 轮或用户显式结束时终止；当前适配器只检查可见的轮次/日期，跨设备和显式结束依赖宿主传入，尚未在适配器层验证。自然日目前按 UTC 日期判定，用户本地时区边界尚待验证。兼容 schema 2 的 `record-turn` 保存当前轮次后若返回 `new_session_required`，提示用户开启新会话，下一轮不得复用原编号。

## 九、持续回访

- 基线完成一个月后进行第一次回访。
- 资料稳定后每季度回访。
- 重大健康、工作、家庭、关系或经济事件随时触发。
- 普通会话候选按每周、每月或用户指定周期集中审核。

回访先问上次确认后发生了什么变化，再检查哪些旧认识被证实、推翻或需要重新解释。
